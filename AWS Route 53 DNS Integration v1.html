SECTION DETAILED STEPS / CONTENT
1. Workshop Objective
Validate AWS Route 53 Resolver integration with the shared DNS VPC (192.168.20.0/24) for exclusive, switchable operation between BlueCat anycast VIP (10.100.100.100) and EfficientIP anycast VIP (192.168.153.153). Azure/GCP clients remain in their respective clouds; AWS workloads and intra-VPC test EC2 instances use Route 53 Resolver rules. All traffic routes via Equinix Fabric + TGW.
2. AWS Route 53 Resolver Concepts
Route 53 Resolver Rules provide conditional forwarding for specific domains (corp.pri., mcd.cloud.) to target IP addresses (anycast VIPs). Rules are associated to one or more VPCs.
  • Resolver Rules: Forwarding equivalent to Azure forwarding rulesets or GCP forwarding zones.
  • Target IP: Any private IP reachable via VPC or TGW (BlueCat/EfficientIP anycast VIPs).
  • Caching follows exact TTL from upstream. Rule changes are immediate for new queries.
  • Reachability: Workloads in same VPC, peered VPCs, or TGW-connected VPCs resolve via Resolver rules. Azure/GCP clients reach VIPs via Equinix Fabric.
Recommendation for POC: Use Resolver rules for precision and simplicity across all AWS workloads.
3. Architecture Constraints
  • DNS appliances run in parallel in the DNS VPC (192.168.20.0/24); VIPs advertised via TGW + FRR/BGP to Equinix Fabric.
  • AWS workloads in same VPC (different subnet) or TGW-connected VPCs use Resolver rules.
  • Azure/GCP client VNets stay in their clouds; no direct VPC peering required.
  • Switching is exclusive; platforms do not run simultaneously.
4. Route 53 Resolver Rules Deployment
One-time AWS CLI commands (BlueCat active):
aws route53resolver create-resolver-rule \
  --name corp-pri-forward \
  --domain-name corp.pri. \
  --rule-type FORWARD \
  --resolver-endpoint-id <optional> \
  --target-ips Ip=10.100.100.100 \
  --tags Key=Purpose,Value=BlueCat

aws route53resolver create-resolver-rule \
  --name mcd-cloud-forward \
  --domain-name mcd.cloud. \
  --rule-type FORWARD \
  --resolver-endpoint-id <optional> \
  --target-ips Ip=10.100.100.100 \
  --tags Key=Purpose,Value=BlueCat

# Associate rules with DNS spoke VPC and any client VPCs
aws route53resolver associate-resolver-rule \
  --resolver-rule-id <rule-id-from-above> \
  --vpc-id vpc-dns-spoke-us-east-2
5. Platform Switching Procedure
Switch to EfficientIP: 
aws route53resolver update-resolver-rule \
  --resolver-rule-id <corp-pri-rule-id> \
  --target-ips Ip=192.168.153.153

aws route53resolver update-resolver-rule \
  --resolver-rule-id <mcd-cloud-rule-id> \
  --target-ips Ip=192.168.153.153
Reverse IPs to switch back. Alternative: delete/re-create rules.
6. Client Configuration
AWS workloads: Associate Resolver rules to target VPCs (DNS spoke + client VPCs). No per-instance DNS change required.
Azure/GCP clients: Update VNet/VPC DNS servers to active VIP (routed via Equinix Fabric + TGW).
7. Testing Scenario: Windows Server in DNS VPC (different subnet)
Deploy a Windows Server 2022/2025 EC2 instance in the DNS VPC (e.g., subnet 192.168.21.0/24).
Steps:
  1. Create EC2; join to corp.root domain.
  2. Set DNS: netsh interface ip set dns "Ethernet" static 10.100.100.100 (BlueCat) or 192.168.153.153 (EfficientIP).
  3. Test: nslookup www.example.com 10.100.100.100 and domain queries.
  4. Switch platform and re-test after TTL expiry + ipconfig /flushdns.
8. AWS Route 53 Resolver Troubleshooting
Key Diagnostic Commands: 
aws route53resolver list-resolver-rules
aws route53resolver list-resolver-rule-associations
aws route53resolver get-resolver-rule --resolver-rule-id <id>
aws ec2 describe-vpcs --vpc-ids vpc-dns-spoke-us-east-2
aws ec2 describe-route-tables --filters Name=tag:Name,Values=*dns*
Common Issues & Resolution:
  1. Resolver rule not resolving: Verify rule association to correct VPC and target VIP reachability; re-create if needed.
  2. BGP/TGW reachability: Confirm TGW route propagation and VIP advertisement.
  3. Azure/GCP clients unreachable: Validate Equinix Fabric BGP and connectivity; test port 53 from Azure/GCP VM.
  4. Stale cache after switch: Wait TTL cycle or run ipconfig /flushdns.
  5. Intra-VPC Windows EC2 fails: Confirm same-VPC subnet, static/DHCP DNS, and security group rules (UDP/TCP 53).

Logging: Enable Route 53 Resolver query logging or VPC Flow Logs / CloudWatch.
9. AWS Route 53 Resolver Caching Behavior Caches per exact TTL from upstream. Rule changes immediate for new queries.
10. Cache Flush Limitations & Workarounds No direct flush; use low TTLs, delete/re-create rules, or client flush.
11. DNS TTL Optimization Strategies (Identical table as Azure/GCP guides – POC: 60–300 s, etc.)
12. Operational Runbook Summary Pre-cutover: lower TTLs + update Resolver rules. Post-cutover: wait TTL cycle + flush. Monitor with dig/nslookup from Azure, GCP, and AWS test EC2.
