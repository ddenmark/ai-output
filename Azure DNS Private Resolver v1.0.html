Azure DNS Private Resolver Integration

Single Resolver • Exclusive Switching • TTL Optimized
SECTION DETAILED STEPS / CONTENT
1. Workshop Objective
Review and validate the integration of a single Azure Private DNS Resolver into the shared DNS VNet (192.168.16.0/24) to support exclusive, switchable operation between BlueCat (anycast VIP 192.168.53.53) and EfficientIP SOLIDserver (anycast VIP 192.168.153.153). Ensure seamless resolution for corp.pri. and mcd.cloud. domains while maintaining global anycast behavior across Equinix Fabric.
2. Architecture Constraints
  • Both BlueCat MDDS + Edge Resolver and EfficientIP SOLIDserver run in parallel in the same DNS VNet (192.168.16.0/24).
  • Anycast VIPs are unique per solution: BlueCat = 192.168.53.53; EfficientIP = 192.168.153.153.
  • Azure does not allow more than one Private DNS Resolver per Virtual Network.
  • Client VNets exist in two regions: East (192.168.4.0/24) and Central (192.168.5.0/24).
  • Azure VNet DNS server settings (dns_servers) are configured only at the VNet level — there is no per-subnet override.
  • Platforms will not run simultaneously; we switch exclusively between BlueCat and EfficientIP.
3. Private DNS Resolver Deployment
A single shared Private DNS Resolver is deployed in the DNS spoke VNet. It provides inbound/outbound endpoints and a forwarding ruleset. Dedicated /28 subnets are carved from the existing 192.168.16.0/20 address space.

One-time Azure CLI commands:
az network vnet subnet create --resource-group rg-bluecat-dns-prod-eastus2 --vnet-name vnet-dns-spoke-eastus2 --name snet-dns-inbound --address-prefixes 192.168.16.240/28 --delegations Microsoft.Network/dnsResolvers
az network vnet subnet create --resource-group rg-bluecat-dns-prod-eastus2 --vnet-name vnet-dns-spoke-eastus2 --name snet-dns-outbound --address-prefixes 192.168.16.224/28 --delegations Microsoft.Network/dnsResolvers

az dns resolver create --resource-group rg-bluecat-dns-prod-eastus2 --name dnspr-bluecat-eastus2 --location eastus2 --virtual-network vnet-dns-spoke-eastus2
az dns resolver inbound-endpoint create --resource-group rg-bluecat-dns-prod-eastus2 --dns-resolver-name dnspr-bluecat-eastus2 --name inbound-ep --subnet snet-dns-inbound --ip-configurations private-ip-address=192.168.16.4
az dns resolver outbound-endpoint create --resource-group rg-bluecat-dns-prod-eastus2 --dns-resolver-name dnspr-bluecat-eastus2 --name outbound-ep --subnet snet-dns-outbound
4. DNS Forwarding Ruleset Configuration
A single ruleset (ruleset-corp) forwards corp.pri. and mcd.cloud. to the active anycast VIP only.

Initial creation (BlueCat active):
az dns resolver forwarding-ruleset create --resource-group rg-bluecat-dns-prod-eastus2 --name ruleset-corp --location eastus2 --dns-resolver-name dnspr-bluecat-eastus2

az dns resolver forwarding-rule create --resource-group rg-bluecat-dns-prod-eastus2 --ruleset-name ruleset-corp --name corp-pri-rule --domain-name corp.pri. --target-dns-servers ip-address=192.168.53.53 port=53
az dns resolver forwarding-rule create --resource-group rg-bluecat-dns-prod-eastus2 --ruleset-name ruleset-corp --name mcd-cloud-rule --domain-name mcd.cloud. --target-dns-servers ip-address=192.168.53.53 port=53
5. Platform Switching Procedure
Switch to EfficientIP:
az dns resolver forwarding-rule update --resource-group rg-bluecat-dns-prod-eastus2 --ruleset-name ruleset-corp --name corp-pri-rule --target-dns-servers ip-address=192.168.153.153 port=53
az dns resolver forwarding-rule update --resource-group rg-bluecat-dns-prod-eastus2 --ruleset-name ruleset-corp --name mcd-cloud-rule --target-dns-servers ip-address=192.168.153.153 port=53
Switch back to BlueCat: reverse the IPs above.

Alternative non-disruptive method: Delete and re-create the two rules using the target VIP for the new platform.
6. Client VNet DNS Server Configuration
Update both client VNets (East and Central) to point exclusively to the active VIP.

# BlueCat active
az network vnet update --resource-group <client-rg> --name vnet-client-eastus --dns-servers 192.168.53.53
az network vnet update --resource-group <client-rg> --name vnet-client-centralus --dns-servers 192.168.53.53

# EfficientIP active (switch)
az network vnet update --resource-group <client-rg> --name vnet-client-eastus --dns-servers 192.168.153.153
az network vnet update --resource-group <client-rg> --name vnet-client-centralus --dns-servers 192.168.153.153
Existing VMs require ipconfig /release && ipconfig /renew (Windows) or NetworkManager restart (Linux).
7. Azure DNS Caching Behavior
  • Azure Private DNS Resolver caches responses from the upstream anycast VIP according to the exact TTL returned by BlueCat Edge Resolver or EfficientIP.
  • Ruleset changes take effect for new queries immediately, but cached entries persist until TTL expiry.
  • Client VMs (Windows/Linux) also cache per-record TTLs and negative responses.
  • VNet dns_servers changes affect new DHCP leases only.
8. Cache Flush Limitations
There is no supported CLI, PowerShell, or API method to flush the Private DNS Resolver cache.

Workarounds (in order of preference):
  1. Low TTLs (60–300 s) on zones during POC.
  2. Delete/re-create forwarding rules (forces re-evaluation).
  3. Client-side: ipconfig /flushdns && ipconfig /release && ipconfig /renew.
  4. Nuclear option: delete/recreate the entire resolver (2–5 min disruption).

10. Operational Runbook Summary & Recommendations
  • Pre-cutover: lower TTLs + update resolver rules + client VNets.
  • Post-cutover: wait one TTL cycle + force client flush.
  • Monitor with dig @192.168.53.53 or dig @192.168.153.153.
  • All changes maintain the single-engineer execution model and global anycast VIP behavior across Equinix Fabric.
