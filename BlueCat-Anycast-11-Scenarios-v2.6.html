Executive Summary

This playbook equips the Global Technology Infrastructure Operations team with everything needed to migrate safely from legacy Microsoft AD DNS to BlueCat MDDS + Edge Resolver anycast DNS. The 11 scenarios cover traffic steering, failover, phased rollout, rollback, security, and rate-limiting — all while preserving the single unified VIP and Market tenant isolation.

Scenario 1: Global Roaming Users — Nearest Most-Available DNS Server (Equal-Cost Anycast)

Roaming store managers, mobile apps, and workloads across NA/Europe/Asia/Latin America must resolve to the topologically closest healthy Edge Resolver VM. The new REGIONAL-ECS VIP (10.100.100.102/32) further enhances this with EDNS Client Subnet geo-steering.

Applied on: All six Edge Resolvers — edge-az-01/02, edge-aws-01/02, edge-gcp-01/02

Edit on: Every Edge Resolver VM (edge-az-01, edge-az-02, edge-aws-01, edge-aws-02, edge-gcp-01, edge-gcp-02)
Example config file path: /etc/frr/frr.conf (or apply via vtysh then write memory) 
# FRR configuration (v2.6) — identical on every Edge Resolver VM
sudo vtysh
configure terminal
ip prefix-list ANYCAST-VIP seq 5 permit 10.100.100.100/32
ip prefix-list ANYCAST-VIP seq 10 permit 10.100.100.102/32
route-map ANYCAST-OUT permit 10
 match ip address prefix-list ANYCAST-VIP
 set metric 0
exit
router bgp 64512
 bgp router-id <VM-PRIMARY-IP>
 neighbor EQUINIX peer-group
 neighbor EQUINIX remote-as 65000
 neighbor EQUINIX route-map ANYCAST-OUT out
 address-family ipv4 unicast
  network 10.100.100.100/32
  network 10.100.100.102/32
  maximum-paths 4
 exit-address-family
write memory
end

Equinix Fabric performs ECMP. On BlueCat Micetro/Edge console, enable ECS for the 10.100.100.102/32 VIP to enable geo-location of the source device IP. Verification: vtysh -c "show ip bgp 10.100.100.102"

Scenario 2: Prefer One Region Over Another (e.g., NA Azure > APAC GCP)

CORP NA workloads prefer Azure Edge Resolvers; APAC traffic falls back only if NA is unhealthy. REGIONAL-ECS VIP (10.100.100.102/32) respects per-region geo-steering.

Applied on: Less-preferred region only (e.g., edge-gcp-01 and edge-gcp-02)

Edit on: Less-preferred region Edge Resolvers only (e.g., edge-gcp-01, edge-gcp-02)
Example config file path: /etc/frr/frr.conf 
route-map ANYCAST-OUT permit 10
 match ip address prefix-list ANYCAST-VIP
 set as-path prepend 64512 64512
 set metric 0
exit
router bgp 64512
 neighbor EQUINIX route-map ANYCAST-OUT out

Preferred region (edge-az-01/02) uses clean route-map from Scenario 1. Equinix selects shortest AS-path.

Scenario 3: Prefer One CSP Over Another (Azure > AWS > GCP)

CORP policy prefers Azure-hosted DNS for performance and cost.

Applied on: All Edge Resolvers with CSP-specific communities

Edit on: All six Edge Resolvers (edge-az-*, edge-aws-*, edge-gcp-* — CSP-specific route-maps)
Example config file path: /etc/frr/frr.conf 
# Azure (edge-az-01/02)
route-map ANYCAST-OUT permit 10
 match ip address prefix-list ANYCAST-VIP
 set community 64512:100 additive
 set metric 0

# AWS (edge-aws-01/02)
 set community 64512:200 additive
 set metric 10

# GCP (edge-gcp-01/02)
 set community 64512:300 additive
 set metric 20

Equinix inbound policy translates communities to Local Preference (200 → 150 → 100).

Scenario 5: Strict CSP Outage Failover Order (Azure → GCP, AWS → GCP, GCP → Azure)

Orderly backup hierarchy during any CSP outage.

Edit on: All six Edge Resolvers (base prepends) + every Edge VM for the script
Example config file path (FRR): /etc/frr/frr.conf
Example script path: /usr/local/bin/dns-health-withdraw.sh 
# Base prepends on each CSP's Edge Resolvers
# Azure (edge-az-*)   → 1× prepend
# AWS (edge-aws-*)    → 2× prepend
# GCP (edge-gcp-*)    → 3× prepend

# Health-check withdrawal script (systemd on every Edge VM)
#!/bin/bash
if ! dig @127.0.0.1 example.com +short > /dev/null; then
  vtysh -c "no network 10.100.100.100/32"
else
  vtysh -c "network 10.100.100.100/32"
fi

Scenario 6: Phased Rollout per Region / CSP / Market (Blast-Radius Control)

Initial implementation operates per-market (NA Market first) while CORP Global services remain available. Market tenants never connect to each other.

Edit on: All six Edge Resolvers (market-specific communities)
Example config file path: /etc/frr/frr.conf 
route-map ANYCAST-OUT permit 10
 match ip address prefix-list ANYCAST-VIP
 set community 64512:MARKET-NA additive   # MARKET-EU, MARKET-APAC, etc.
exit
router bgp 64512
 neighbor EQUINIX route-map ANYCAST-OUT out

Equinix inbound policy filters advertisements per-market community.

Scenario 7: Zero-Downtime Rollback to Legacy Microsoft AD DNS

If migration introduces unexpected latency or resolution failures, instantly fall back to existing MS DNS anycast VIP 10.100.100.99/32.

Edit on: All six Edge Resolvers (increase prepend or withdraw)
Example config file path: /etc/frr/frr.conf or run the health-withdraw script

Pre-advertise legacy VIP with higher Local Preference (community 64512:999). On rollback: increase prepend to 10× on all BlueCat Edge VMs or withdraw BlueCat VIP via health-check script. Revert completes in <60 seconds via Ansible.

Scenario 8: Human-Error Mitigation & Operational Safeguards

Prevent accidental configuration errors during 24×7 operations.

  • Terraform/Ansible dry-run + Azure DevOps approval gates
  • Change windows restricted to low-traffic hours per Market
  • BlueCat Micetro shadow mode + route-map versioning
  • Pre-staged rollback route-maps (single vtysh command)
  • Prometheus + FRR exporter alerts on unexpected BGP changes

Scenario 9: Shadow Mode Co-Existence During Migration

Run BlueCat Edge Resolvers in parallel with legacy MS DNS while gradually shifting clients.

Edit on: All six Edge Resolvers (shadow community)
Example config file path: /etc/frr/frr.conf 
route-map ANYCAST-OUT permit 10
 match ip address prefix-list ANYCAST-VIP
 set community 64512:SHADOW additive   # lower Local Preference
exit

BlueCat Edge forwards unresolved queries to legacy MS DNS via Micetro. After 72-hour monitoring, raise community preference and deprecate MS DNS.

Scenario 10: BGP Session Authentication + Strict Prefix Filtering

Protect against route hijacks or accidental leaks between isolated Market tenants and CORP global services.

Edit on: All six Edge Resolvers (edge-az-*, edge-aws-*, edge-gcp-*)
Example config file path: /etc/frr/frr.conf 
# FRR on every Edge Resolver (edge-az-*, edge-aws-*, edge-gcp-*)
router bgp 64512
 neighbor EQUINIX password <strong-shared-secret>   # MD5 or TCP-AO
 neighbor EQUINIX prefix-list ANYCAST-ONLY out
!
ip prefix-list ANYCAST-ONLY seq 5 permit 10.100.100.100/32
ip prefix-list ANYCAST-ONLY seq 10 deny any

Equinix Fabric: strict inbound prefix-list, maximum-prefix limit, authentication required.

Scenario 11: DNS Rate-Limiting to Protect 24×7 Restaurant POS Systems

Prevent query floods from the 48,000 always-on POS terminals across global markets that could overwhelm the anycast DNS during peak hours or due to misconfigured devices.

Applied on: All six Edge Resolver VMs + BlueCat Micetro console

Edit on: Every Edge Resolver VM (nftables) + Micetro console policy
Example config file path (nftables script): /usr/local/bin/pos-rate-limit-v2.6.sh (run once or via systemd)
Micetro path: Micetro → Policies → Query Rate Limit (global or per-market) 
# nftables rate-limiting (v2.6) — apply on every Edge Resolver VM
sudo nft add table inet dns_rate_limit
sudo nft add chain inet dns_rate_limit input { type filter hook input priority 0\; policy accept\; }
sudo nft add rule inet dns_rate_limit input ip saddr 192.168.0.0/16 udp dport 53 limit rate 50/second burst 100 packets accept
sudo nft add rule inet dns_rate_limit input ip saddr 192.168.0.0/16 tcp dport 53 limit rate 30/second burst 50 packets accept
sudo nft add rule inet dns_rate_limit input ip saddr 192.168.0.0/16 udp dport 53 counter drop
sudo nft add rule inet dns_rate_limit input ip saddr 192.168.0.0/16 tcp dport 53 counter drop

# BlueCat Micetro policy (global or per-market)
# Query Rate Limit: 200 qps per source IP for POS subnets
# Burst: 500 queries
# Action on exceed: Drop + syslog to Micetro Analytics

POS subnets (e.g., 192.168.0.0/16) are rate-limited to protect restaurant operations while allowing legitimate CORP/Market traffic. Alerts feed into BlueCat Analytics for immediate visibility.
