BlueCat MDDS + Edge Resolver Security Testing Runbook

RPZ • TSIG • Rate Limiting • SIEM • DNS Views • Sinkholing
SECTION DETAILED STEPS
1. Workshop Objective
Validate all security controls for BlueCat MDDS (authoritative) + Edge Resolver (recursive) anycast deployment in the shared DNS VPC (192.168.30.0/24) across Azure, AWS, and GCP. Confirm RPZ, TSIG, rate limiting, DNSSEC, BGP health-based withdrawal, SIEM integration, alerting, DNS Views, and sinkholing function correctly while maintaining CORP/Market tenant isolation and global 24×7 restaurant operations.
QSR Relevance: These controls enforce strict tenant isolation between Market entities and CORP global services, protect against external threats at peak traffic hours, and provide audit-ready evidence for compliance.
2. Prerequisites
  • Micetro Central console access with DDI-Engineer role
  • Windows 11 test VMs in East/Central client VNets and intra-VPC Windows Server in DNS spoke
  • dnsperf, PowerShell 7+, Flamethrower (optional) installed on test clients
  • FRR/BGP peering Established for 10.100.100.100/32
  • Corporate SIEM (Splunk/Azure Sentinel) endpoint configured for syslog
  • BlueCat Analytics dashboard access enabled
Tip: All test clients should already point to the unified anycast VIP 10.100.100.100. No client-side DNS changes are required for Views or sinkholing tests.
3. Server-Side Testing (MDDS + Edge Appliances)
3.1 RPZ Threat Feed Blocking
1. Log into Micetro Central console → navigate to DNS → Resolver → select one of the Edge Resolver instances → click the Advanced tab → scroll to Response Policy Zones section.
2. Click “Import” and upload a test RPZ feed file (example: Malware Domain List CSV containing domains such as “malware.example.test”).
3. Apply and save the policy to all Edge Resolver instances (Azure, AWS, GCP).
4. From any test client VM run: nslookup known-bad-domain.test 10.100.100.100.
5. Verify the response is NXDOMAIN or redirected to the configured sinkhole IP.
6. Check Micetro audit log (Administration → Audit) and Edge resolver logs for the RPZ hit entry.
Expected Result: Malicious domains are blocked instantly. QSR Benefit: Prevents phishing and malware callbacks from restaurant POS systems.
3.2 Rate Limiting & DoS Protection
1. SSH to each Edge VM and verify the rate-limit rule: sudo nft list ruleset | grep 50.
2. From a single test VM launch a flood exceeding 50 QPS, for example using PowerShell: 1..20000 | ForEach-Object -Parallel { Resolve-DnsName -Name www.example.com -Server 10.100.100.100 -Quick } -ThrottleLimit 100 or dnsperf command: dnsperf -s 10.100.100.100 -d queries.txt -c 100 -l 30.
3. Monitor Edge VM CPU/memory via htop and nftables counters with sudo nft list ruleset.
4. Confirm legitimate queries from a second client continue without interruption.
5. Verify dropped packets appear in Edge logs.
Expected Result: Excess queries are dropped while valid traffic flows. QSR Benefit: Maintains DNS availability during DDoS events at 48,000 restaurants.
3.3 ACLs & Zone Transfer Controls
1. In Micetro → Zone → select corp.pri. → Properties → TSIG/ACLs tab: restrict AXFR/IXFR to only Micetro Central IP and hidden master IPs.
2. From an unauthorized test VM run: dig @10.100.100.100 corp.pri. AXFR.
3. Confirm response is REFUSED or connection timeout.
4. From authorized Micetro server repeat the same dig command and confirm successful full zone transfer.
Expected Result: Zone transfers are denied to unauthorized clients.
3.4 DNSSEC Validation
1. In Micetro Central → DNS → Resolver → select Edge Resolver → Advanced tab: enable “DNSSEC Validation” and apply to all Edge nodes.
2. From test client run a signed domain query: dig +dnssec example.com @10.100.100.100 (look for “AD” flag in output confirming validation).
3. Simulate forged response (concrete lab example): On a Linux test VM install scapy (sudo apt install python3-scapy), create a short script to craft and send a UDP packet with an invalid RRSIG signature for the same domain (or use a pre-built test tool such as “dnssec-forgery” script). Alternatively, temporarily create a test zone in Micetro with a deliberately bad DNSSEC record and query it from the Edge Resolver.
4. Confirm the Edge Resolver returns SERVFAIL on the forged query.
Expected Result: Valid DNSSEC queries succeed; forged or tampered responses are rejected with SERVFAIL. QSR Benefit: Protects against cache poisoning attacks that could redirect restaurant traffic to malicious sites.
3.5 BGP Health-Based Withdrawal
1. SSH to one Edge VM and simulate high CPU load: stress --cpu 8 --timeout 60.
2. Immediately monitor BGP status: vtysh -c "show ip bgp summary" and vtysh -c "show ip bgp 10.100.100.100".
3. Confirm the 10.100.100.100/32 prefix is withdrawn from that node within <5 seconds.
4. From a client VM run continuous while true; do nslookup www.example.com 10.100.100.100; sleep 0.5; done and verify traffic automatically shifts to remaining healthy Edge nodes with zero resolution loss.
4. Client-Side Testing (Windows 11 Workstations)
4.1 TSIG-Secured DDNS Updates
1. In Micetro → Administration → TSIG Keys: generate key named “qsr-ddns-tsig” (HMAC-SHA256) and assign it to the relevant zones.
2. Push the TSIG key via GPO to Windows 11 clients (Group Policy → Computer Configuration → Administrative Templates → Network → DNS Client).
3. On a test client run: ipconfig /registerdns.
4. Verify the signed update appears in Micetro audit log with “TSIG” indicator.
5. Temporarily remove the key from the zone and repeat step 3; confirm the update is rejected with “Refused” status.
QSR Relevance: Prevents unauthorized dynamic updates from compromised restaurant workstations.
4.2 DNS Query Flooding & Rate-Limit Impact
1. From four Windows 11 VMs simultaneously run the parallel flood: 1..10000 | ForEach-Object -Parallel { Resolve-DnsName -Name www.example.com -Server 10.100.100.100 -Quick } -ThrottleLimit 200.
2. Monitor anycast VIP reachability and Edge rate-limit counters in real time.
3. Confirm consistent resolution for non-flood clients running normal queries in parallel.
4.3 Cache Poisoning & Spoofing Resistance
1. From a test client issue a recursive query: nslookup www.microsoft.com 10.100.100.100.
2. On a second Linux VM use a packet-crafting tool (e.g., scapy or hping3) to inject forged UDP responses with incorrect data on port 53.
3. Confirm the Edge Resolver drops the forged packets due to source-port randomization and DNSSEC validation.
4.4 Client Failover During Platform Switch
1. On a client run a continuous loop: while true; do nslookup www.example.com 10.100.100.100; sleep 0.3; done.
2. Perform platform switch (Edge → EfficientIP) by updating forwarding rules/zones in Micetro.
3. After one TTL cycle run ipconfig /flushdns and confirm resolution switches with no interruption.
5. Real-World Scenarios
5.1 External DDoS on Anycast VIP (Peak-Hour Restaurant Traffic)
1. Coordinate with test team to launch sustained 10k+ QPS flood from external Azure test VMs targeting 10.100.100.100:53.
2. Monitor Equinix Fabric BGP sessions and Edge nftables counters in real time.
3. Trigger health-based withdrawal on the overloaded Edge node.
4. Measure client resolution success rate and BGP convergence time (<5 seconds target).
5.2 Insider Threat – Unauthorized Dynamic Update from Market Tenant
1. From a Market VNet test VM attempt DDNS update without valid TSIG key: ipconfig /registerdns.
2. Confirm Micetro rejects the update and logs the event with “TSIG failure”.
3. Verify CORP zones remain untouched and no data leakage occurs.
5.3 Cache Poisoning Attempt During Recursive Resolution
1. Simulate phishing campaign by injecting forged responses for a high-traffic external domain (e.g., payment gateway).
2. Confirm DNSSEC validation + RPZ policy blocks the attempt.
3. Verify the incident is logged in Micetro and forwarded to SIEM.
5.4 BGP Hijack / Route Leak During Maintenance
1. From one cloud intentionally advertise a more-specific route or excessive AS-path prepend.
2. Monitor Equinix Fabric route preference and BGP attributes.
3. Confirm traffic automatically shifts to the healthiest anycast paths with zero client impact.
5.5 Ransomware Callback Blocking (Restaurant POS Infection)
1. Add known ransomware callback domains (e.g., “ransom-c2.example”) to the active RPZ feed.
2. From a simulated infected POS test VM query the callback domain.
3. Confirm immediate sinkhole redirect or NXDOMAIN.
4. Verify audit log entry and SIEM alert fire within seconds.
5.6 DNS Tunneling / Data Exfiltration Attempt
1. Use dns2tcp or a similar tool from a test VM to generate long TXT/NULL queries simulating data exfiltration.
2. Monitor Edge Resolver query logs for anomalous patterns (high volume of unusual record types).
3. Confirm rate limiting or custom RPZ policy blocks the tunnel.
4. Verify the corresponding alert is raised in SIEM.
5.7 Market Tenant Accessing CORP Payment Services (Isolation Test)
1. From a Market test VM attempt to resolve a CORP-only payment gateway domain (e.g., “pay.corp.pri.”).
2. Confirm the DNS View “market-restricted” returns NXDOMAIN or sinkhole.
3. From a CORP test VM repeat the query and confirm successful resolution.
4. Validate complete isolation between Market entities.
5.8 Threat Intelligence Feed Update Validation
1. Update the active RPZ feed with newly published threat domains.
2. Immediately query the newly added malicious domain from multiple client VNets.
3. Confirm blocking occurs within 60 seconds of feed ingestion across all Edge nodes.
4. Verify propagation and statistics in the Micetro Analytics dashboard.
6. SIEM Integration, Alerting & Monitoring
6.1 SIEM Integration & Log Forwarding
1. In Micetro → Administration → Logging: enable syslog forwarding and configure the corporate SIEM endpoint (Splunk/Azure Sentinel).
2. In BlueCat Analytics → Settings: enable forwarding of DNS query logs, audit events, and RPZ hits.
3. On each Edge VM configure rsyslog to forward nftables and FRR logs to the same SIEM.
4. Generate test events (RPZ hit, TSIG failure, rate-limit breach).
5. Verify all events appear correlated in SIEM with correct timestamps and metadata.
6.2 Real-Time Alerting on Anomalous DNS Activity
1. In Micetro → Analytics → Alerts: create rules for >500 QPS from single IP, RPZ hits >10/min, TSIG failures >5/min.
2. Configure alert actions (email notification + PagerDuty webhook).
3. Trigger an anomaly (e.g., query flood or invalid TSIG update).
4. Confirm alert fires within 30 seconds and includes full context (source IP, domain, Edge node).
6.3 Centralized Monitoring Dashboard Validation
1. Log into BlueCat Analytics → Dashboard and verify real-time widgets for query volume by cloud/Edge node, BGP peer status, RPZ block statistics, and cache hit/miss ratio.
2. Simulate failover by stopping one Edge node.
3. Confirm dashboard updates within 10 seconds and clearly shows automatic traffic shift to remaining nodes.
4. Export the 72-hour baseline report for production cutover reference.
7. DNS Views & Sinkholing for Tenant Isolation
7.1 DNS Views Configuration (Split-Horizon / Restricted Resolution)
1. In Micetro Central → Administration → DNS Views → click “Create” and name the new view “market-restricted”.
2. In the ACL section add all Market VNet CIDR blocks (example: 192.168.4.0/24 East, 192.168.5.0/24 Central, etc.).
3. Switch to the “market-restricted” view, select CORP-only zones (corp.pri., mcd.cloud.) and set the response type to “Deny” or leave the record set empty.
4. Apply the view to all Edge Resolver instances in the shared DNS VPC.
5. From a CORP test client run: nslookup internal-service.corp.pri. 10.100.100.100 (should resolve normally).
6. From a Market test client repeat the identical query (should return NXDOMAIN or empty response).
Additional Information: DNS Views allow the same anycast VIP 10.100.100.100 to serve completely different answers based on the client’s source IP, enforcing strict CORP/Market isolation without any client-side DNS reconfiguration.
7.2 DNS Sinkholing Integration (RPZ + Views)
1. In Micetro → DNS → Response Policy Zones → create or edit a sinkhole policy.
2. Define a sinkhole IP (example: 10.100.100.999 pointing to a dedicated blackhole VM or null route).
3. Link the sinkhole policy to both the default view and the newly created “market-restricted” view.
4. For any restricted zones/records change the action from “Deny” to “Sinkhole”.
5. Apply the updated policy to all Edge Resolvers.
6. From a Market client query a restricted domain and confirm the response redirects to the sinkhole IP.
7. Verify the sinkhole action is recorded in Micetro audit log and Edge resolver logs.
Expected Result: Restricted clients are silently redirected to a sinkhole instead of receiving a plain NXDOMAIN, improving logging and threat-intelligence collection.
7.3 Combined View + Sinkhole Testing
1. Simultaneously run continuous queries from both CORP and Market test clients.
2. Confirm CORP clients receive full, normal resolution while Market clients are either denied or redirected to the sinkhole IP.
3. Validate that tenant isolation is fully enforced while all clients continue using the single unified anycast VIP 10.100.100.100.
