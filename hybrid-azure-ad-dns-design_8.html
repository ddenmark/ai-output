Executive Summary

This document defines a production-grade hybrid Active Directory and DNS architecture that extends corp.local into Azure, providing the identity, networking, security, and disaster-recovery foundation for a phased migration of on-premises workloads from Orlando (primary) and Franklin (DR) into Azure US East 2, with US Central as the DR region. Regional Azure domain controllers act as primary DNS, all traffic is inspected through a hub-and-spoke security fabric, and a protection-first sequence lands every migrated workload with DR coverage active from day one.

Prerequisites

Four readiness tracks — expand each for full detail.

01 Azure Networking

Core Network Topology

  • Hub VNet in us-east-2 (example: 10.10.0.0/16) and us-central (example: 10.20.0.0/16).
  • Hub-to-spoke VNet peering with transitive routing enabled (or UDRs via CloudGuard if needed).

ExpressRoute + Megaport 10Gig Connectivity (Leading Practices)

  • Use 10 Gbps Megaport cloud connects from both Orlando and Franklin datacenters to Azure (redundant circuits per region recommended).
  • Deploy ExpressRoute gateways in UltraPerformance or ErGw3AZ SKU in each regional hub for high throughput and zone redundancy.
  • Advertise on-prem routes (including DNS server subnets) via BGP over ExpressRoute.
  • Enable Private Peering only (avoid Microsoft Peering unless required):
    • Private Peering — exchanges routes between on-premises and Azure VNets privately. This is what you need for hybrid connectivity, DNS resolution to Private Endpoints, and workload communication.
    • Microsoft Peering — connectivity to Microsoft cloud services (Office 365, Azure public PaaS) over ExpressRoute. More expensive, adds route-filtering complexity. Only enable for a specific requirement to route Microsoft SaaS over ExpressRoute instead of the public internet.

Inspect ExpressRoute Gateways & BGP

  1. In Azure Portal: go to each ExpressRoute circuit → Gateways → review SKU, utilization, and BGP status.
  2. Run az network express-route gateway list --resource-group <rg> to review gateway details and BGP settings.
  3. Check BGP routes advertised/received using Get-AzExpressRouteCircuitRouteTable (PowerShell) or via Check Point CloudGuard logs / SmartConsole.
  4. Verify route propagation into the hub VNet route table.

Network Troubleshooting: Traceroute & ICMP Requirements

Important: Traceroute relies on specific ICMP message types. These must be allowed through NSGs, CloudGuard policies, and any on-prem firewalls for effective troubleshooting.

Required ICMP types:

  • ICMP Type 11, Code 0 — Time Exceeded (TTL expired in transit). Most critical for traceroute to function.
  • ICMP Type 8 — Echo Request (used by ping)
  • ICMP Type 0 — Echo Reply (response to ping)
  • ICMP Type 3 — Destination Unreachable (various codes, useful for diagnostics)

Steps to run traceroute:

from on-prem / Azure VM
tracert <Azure VM private IP>          # Windows
traceroute <Azure VM private IP>       # Linux

# From Check Point CloudGuard CLI (advanced):
traceroute <destination>
Tip
If traceroute stops at CloudGuard or an NSG, verify that ICMP Type 11 (Time Exceeded) is permitted in the relevant security policies / NSG rules.

Check Point CloudGuard + Azure Route Server — Architecture Options

Four escalating complexity levels. Most environments start at Level 1.

Level 1 — Simple: UDRs + Load Balancer (most common starting point)
  • Deploy CloudGuard behind an Azure Load Balancer (Standard SKU).
  • Use static User Defined Routes (UDRs) in hub and spoke subnets pointing to the LB frontend IP (or directly to CloudGuard private IP in active/passive designs).
  • Simple to implement and troubleshoot.
  • Downside: manual route management — changes require updating UDRs across multiple subnets.
Level 2 — Medium: Azure Route Server (without BGP to NVA)
  • Deploy Azure Route Server in the hub VNet.
  • Route Server learns routes dynamically from ExpressRoute and VPN connections.
  • You still use UDRs to steer traffic to CloudGuard for inspection.
  • Benefit: reduces manual route management for learned on-prem and cross-region routes.
  • Does not eliminate the need for UDRs to force traffic through the NVA.
Level 3 — Advanced: Azure Route Server + BGP peering to CloudGuard
  • CloudGuard establishes BGP peering with Azure Route Server.
  • Routes exchanged dynamically between on-prem, CloudGuard, and Azure VNets.
  • Can reduce (but usually not completely remove) static UDRs for some traffic patterns.
  • Still typically requires some UDRs or custom routing to force traffic through CloudGuard (Azure does not automatically send all traffic through an NVA).
  • Higher operational complexity; requires careful BGP design (AS numbers, route filtering, etc.).
Level 4 — Most Complex: Full dynamic routing + Route Server everywhere
  • On-prem edge, CloudGuard, Azure Route Server, and potentially Spoke Route Servers all participate in BGP.
  • Maximum automation and resilience.
  • Highest complexity — requires deep expertise in BGP, route filtering, and Azure networking.
  • Recommended only for very large-scale or highly dynamic environments.
Key Reality Check
Even when using Azure Route Server + BGP peering with CloudGuard, you will almost always still need some form of UDRs (or equivalent) to force traffic through the inspection point. Azure Route Server excels at route propagation, not at replacing the need to steer traffic through an NVA like CloudGuard.

Traffic Engineering & BGP Control to Azure

Context
All connections are 10 Gbps via Megaport. Significantly more workloads originate from Orlando than Franklin. Goal: optimize for latency + performance while maintaining resilience.
Scenario 1: Primary — Orlando prefers US East 2 Recommended

Technique: AS Path Prepending from Orlando edge / Check Point.
Implementation: prepend AS path 2–3 times when advertising routes via Franklin circuit or Central region.
Effect: Azure prefers Orlando → East path for return traffic due to shorter AS path.
Latency Benefit: lowest-latency path for the majority of workloads.

Scenario 2: Balanced Load — Orlando + Franklin both prefer East

Technique: minimal or no prepending from Orlando + moderate prepending from Franklin.
Use Case: when you want both datacenters to primarily use East (more capacity or lower latency) but still have Central as backup.
Risk: can lead to asymmetric routing if not combined with UDRs.

Scenario 3: Regional Affinity — Orlando → East, Franklin → Central

Technique: AS Path Prepending + Local Preference tuning.
Implementation: Orlando prepends when going to Central; Franklin prepends when going to East.
Benefit: reduces cross-region traffic and potential hairpinning through one CloudGuard instance.
Best for: large deployments with clear regional workload distribution.

Scenario 4: Full Mesh / Maximum Resilience — all paths active

Technique: equal-cost or near-equal paths with no heavy prepending.
Use Case: automatic load balancing across all 10Gig links and both regions.
Downside: less predictable traffic patterns, harder to troubleshoot. Not recommended unless you have advanced monitoring.

Scenario 5: Migration Lifecycle — Franklin origin shifts over time Phased

Franklin-originated traffic deliberately changes path as the migration matures. This is driven by where the replication aggregation point lives and, later, by DR affinity.

 During Migration — Franklin → Orlando → US East 2

The Azure Migrate appliance / replication aggregation point is hosted in Orlando. Franklin source servers replicate to Orlando first, which forwards into US East 2 over the Orlando circuit.

Mechanism: PBR (source-based) on the Franklin edge sends replication-class traffic to the Orlando aggregation subnet; Orlando forwards to East. Production Franklin traffic is unaffected.
 Post-Migration — Franklin → US Central (direct)

Once Franklin workloads are migrated and DR is established, Franklin-origin traffic targets US Central directly over the Franklin circuit for DR-region affinity.

Mechanism: remove the Orlando-aggregation PBR; raise Local Preference for the Franklin→Central circuit and AS-path-prepend Franklin advertisements toward East so Central wins for Franklin prefixes.

Cutover trigger: flip the PBR / BGP attributes only after Azure Migrate cutover completes and the Central DR landing zone is validated. Until then, keep the Orlando aggregation path to avoid re-baselining replication.

Leading Practices for This Architecture
  • Primary Recommendation: Orlando → US East 2 as primary path (AS Path Prepending from Franklin/Central). Aligns with workload distribution and latency.
  • Return Path Control: use AS Path Prepending from on-prem. Avoid relying only on Azure-side controls if possible.
  • Combine with UDRs: use CloudGuard UDRs in Azure to control which workloads are forced through inspection vs direct routing.
  • Monitor Asymmetry: asymmetric routing is acceptable if CloudGuard is not in the path for all traffic. Document expected flows.
  • Test Failover Regularly: simulate circuit/gateway failures quarterly. Validate DNS resolution and application performance during failover.
  • BGP Communities: if Megaport/provider supports them, use communities for more granular control instead of (or in addition to) AS Prepending.
  • Avoid Over-Prepending: prepending more than 3–4 times can make a path completely unusable even as backup.

UDRs per CloudGuard Firewall Set — Forcing NVA Inspection for All VNets

Each region runs its own CloudGuard set behind an internal load balancer (ILB). Route tables force every VNet's east-west, internet, and on-prem traffic through that ILB front-end as a VirtualAppliance next hop. Next-hop convention: East ILB 10.10.30.4, Central ILB 10.20.30.4.

Loop & symmetry rules (apply to every table)
  • Never put a force-to-NVA route on the CloudGuard subnet itself — it would loop. The NVA subnet egresses 0.0.0.0/0 → Internet and reaches on-prem via VirtualNetworkGateway.
  • Set "Propagate gateway routes" = Disabled on all inspected subnets so BGP on-prem routes can't bypass the NVA.
  • Put the matching return-path UDR on the GatewaySubnet so on-prem→spoke replies are symmetric (also through the NVA).
  • Keep Private Endpoint subnet traffic on system routes unless policy requires inspection — hairpinning PE traffic through the NVA adds latency.

02 On-Premises

Core On-Prem DNS Configuration

  • Windows Server AD-integrated DNS on Orlando and Franklin DCs hosting the corp.local zone.
  • Static private IPs for DNS servers (reachable via ExpressRoute). Example: Orlando-DC01 = 192.168.1.10, Franklin-DC01 = 192.168.2.10 (update with actual IPs).
  • No existing conditional forwarders for Azure privatelink.* zones (as stated).

Verification Steps for DNS Server Configuration

Tools required:

  • DNS Manager (dnsmgmt.msc)
  • PowerShell (with DNS Server module)
  • repadmin.exe, dcdiag.exe
  • NSLookup, TCPing, or PsPing for connectivity testing
  • Remote Desktop (RDP) console access to all DCs

Verification checklist (run on Orlando-DC01, Orlando-DC02, Franklin-DC01, Franklin-DC02):

  1. Root Hints: DNS Manager → right-click server → Properties → Root Hints tab. Verify standard root hints are present (or forwarders are configured instead).
  2. Forwarders: server Properties → Forwarders tab. Document any existing forwarders (especially to ISP or other internal DNS).
  3. Conditional Forwarders: expand Conditional Forwarders folder. Confirm there are currently no entries for privatelink.* zones.
  4. Stub Zones: check for any stub zones (especially Azure or partner domains). Document if present.
  5. DC DNS Server Settings: on each DC, run Get-DnsClientServerAddress -AddressFamily IPv4. Ensure DCs point to each other (or loopback + partner), not external DNS.

04 Private Endpoint Placement Strategy

Choosing where to place Private Endpoints (hub vs spokes) has significant impact on security, performance, manageability, and on-prem access.

Hub-Level PEs (Centralized)
Use cases: centralized logging / diagnostic storage, shared Key Vault for core infra, common Azure Files shares, Azure Monitor / Log Analytics storage targets.
Advantages: easier on-prem access (single set of IPs), centralized inspection via CloudGuard, simpler DNS zone management, better for core/shared services.
Disadvantages: potential bottleneck / larger blast radius, more complex routing/UDRs in hub, less aligned with landing-zone isolation.
Spoke-Level PEs (Distributed)
Use cases: application-specific storage accounts, Azure Files per app, App Service / Function App storage, workload-specific Key Vaults.
Advantages: better security isolation per app/team, follows Azure Landing Zone best practices, smaller blast radius, easier to scale & delegate ownership.
Disadvantages: more complex on-prem access (many PEs), harder to centrally inspect all PE traffic, requires good DNS & routing automation.
Recommendation for Your Environment
  • Use Hub-level PEs for core infrastructure services (centralized logging, shared monitoring storage, common Key Vaults).
  • Use Spoke-level PEs for application workloads and team-specific storage.
  • Consider a hybrid approach: centralized PE subnet in hub for shared services + dedicated PE subnets in spokes for applications.
  • Ensure proper NSG + ASG strategy and centralized Private DNS Zone management regardless of placement.
05 Planning Decisions
  • Centralized zones + ruleset approach (recommended): link private DNS zones to hubs (and spokes). Use rulesets mainly for corp.local forwarding.
  • Alternative (decentralized): keep spokes on Azure-provided DNS (168.63.129.16) and forward private zones via ruleset to inbound IP. More complex; avoid unless you have specific isolation needs.
  • Scope of forwarding: specific privatelink.* zones (safer, avoids split-brain) vs. broader suffixes.

Why specific zones? (Important best practice)

Using only specific privatelink.* zones is strongly recommended over forwarding broader Azure namespaces (e.g. blob.core.windows.net).

  • Prevents accidental private resolution of public resources: forwarding a broad zone means any Storage Account without a Private Endpoint still resolves — but returns the public IP, sending traffic over the public internet instead of staying private.
  • Avoids split-brain DNS conflicts: broader forwarding increases the chance of name collisions or unexpected behavior between public and private resources.
  • Security & predictability: specific zones ensure only services you explicitly enabled with Private Endpoints resolve privately. Everything else behaves normally.
  • Some orgs do forward broader zones (entire core.windows.net or azure.net) but must accept that non-PE services return public IPs. Requires careful management and is generally discouraged unless there's a specific operational reason.

Recommendation: stick to specific privatelink.* zones for the services you actually use with Private Endpoints — the cleanest and safest approach for most hybrid environments.

Azure Policy for Automatic Private DNS Zone Groups

This policy automatically creates and links a Private DNS Zone Group whenever a new Private Endpoint is created — a key governance control for your hybrid environment.

Required Access / Permissions
  • Create Policy Definitions: Microsoft.Authorization/policyDefinitions/write (typically requires Owner or custom role at Subscription or Management Group scope).
  • Assign policies + remediation tasks: Microsoft.Authorization/policyAssignments/write + Microsoft.Authorization/roleAssignments/write (usually Owner or User Access Administrator).
  • Recommended role combination: Policy Contributor + User Access Administrator at the target Management Group or Subscription.
  • Additional: permissions to read and link the target Private DNS Zones.

Step-by-Step Setup

  1. Pre-create your Private DNS Zones — create all required zones (e.g. privatelink.blob.core.windows.net, privatelink.vaultcore.azure.net, etc.) in a centralized subscription and link them to your Hub VNets in both regions.
  2. Create the Custom Policy Definition — via Azure Portal, CLI, PowerShell, or Bicep/ARM. Key components:
    • Effect: deployIfNotExists
    • Target resource type: Microsoft.Network/privateEndpoints
    • Existence condition: check if a privateDnsZoneGroups resource already exists for this PE
    • Deployment: ARM template that creates/updates the privateDnsZoneGroups linked to your pre-defined zones
Example 1 — Net New Private DNS Zone Group (create if not exists)
policy definition · deployIfNotExists
{
  "if": { "field": "type", "equals": "Microsoft.Network/privateEndpoints" },
  "then": {
    "effect": "deployIfNotExists",
    "existenceCondition": {
      "field": "Microsoft.Network/privateEndpoints/privateDnsZoneGroups",
      "exists": false
    },
    "deployment": {
      "properties": {
        "mode": "incremental",
        "template": {
          "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#",
          "contentVersion": "1.0.0.0",
          "resources": [{
            "type": "Microsoft.Network/privateEndpoints/privateDnsZoneGroups",
            "apiVersion": "2023-11-01",
            "name": "[concat(parameters('privateEndpointName'), '/default')]",
            "properties": {
              "privateDnsZoneConfigs": [
                { "name": "blob", "properties": { "privateDnsZoneId": "[parameters('blobZoneId')]" } },
                { "name": "file", "properties": { "privateDnsZoneId": "[parameters('fileZoneId')]" } }
              ]
            }
          }]
        },
        "parameters": {
          "privateEndpointName": { "value": "[field('name')]" },
          "blobZoneId": { "value": "[parameters('blobZoneResourceId')]" },
          "fileZoneId": { "value": "[parameters('fileZoneResourceId')]" }
        }
      }
    }
  }
}
Example 2 — Update Existing Zone Group (add additional domain)

For existing zone groups, policies typically cannot easily "merge" — instead use a remediation task or redeploy with all desired zones. A common pattern is to always deploy the full desired list of zones:

policy definition · full desired list

  "then": {
    "effect": "deployIfNotExists",
    "existenceCondition": {
      "allOf": [
        { "field": "Microsoft.Network/privateEndpoints/privateDnsZoneGroups", "exists": true }
      ]
    },
    "deployment": {
      "properties": {
        "mode": "incremental",
        "template": {
          "$schema": "...",
          "resources": [{
            "type": "Microsoft.Network/privateEndpoints/privateDnsZoneGroups",
            "name": "[concat(parameters('privateEndpointName'), '/default')]",
            "properties": {
              "privateDnsZoneConfigs": [
                { "name": "blob",  "properties": { "privateDnsZoneId": "[parameters('blobZoneId')]" } },
                { "name": "file",  "properties": { "privateDnsZoneId": "[parameters('fileZoneId')]" } },
                { "name": "vault", "properties": { "privateDnsZoneId": "[parameters('vaultZoneId')]" } }  // Additional domain
              ]
            }
          }]
        }
      }
    }
  }
}

Note: for true "update existing" behavior, many teams run a remediation task after policy assignment or use a separate initiative that re-applies the full desired zone list.

  1. Assign the Policy — recommended scope: Management Group (Connectivity or Landing Zones level). Provide parameters: array/list of your Private DNS Zone resource IDs. Enable Remediation so existing Private Endpoints are also updated.
  2. Test the Policy — create a new Private Endpoint in a spoke and verify a Private DNS Zone Group is automatically created and linked to your centralized zones.

  • US Central Hub: snet-cloudguard (recommended /26, e.g. 10.20.30.0/26)

These subnets should be dedicated to CloudGuard with minimal other resources.

Step 2 — Create NSG for the Gateway Subnet

  • Allow health-probe traffic from Azure Load Balancer (typically 8117 for Check Point).
  • Allow management ports from Bastion / admin subnets (SSH, SmartConsole).
  • Allow VPN / IPsec traffic if using Site-to-Site VPN (UDP 500, 4500).
  • Allow other traffic as needed for inspection (can be broad since traffic is steered via UDRs).

Step 3 — Deploy CloudGuard Auto Scaling (VMSS + Load Balancer)

  1. In the Azure Marketplace, search for Check Point CloudGuard Network Security.
  2. Choose the Auto Scaling deployment option.
  3. Configure: VMSS in the dedicated snet-cloudguard; Azure Load Balancer (Standard SKU) in front; health probe (typically port 8117); autoscale rules based on CPU/memory or custom metrics; assign a public IP (if needed for VPN) or keep private-only.
  4. Complete the deployment and verify multiple gateway instances are running.

Step 4 — (Optional but Powerful) Deploy Azure Route Server

  1. Deploy Azure Route Server in a dedicated subnet in each hub VNet.
  2. Peer it with ExpressRoute gateways and CloudGuard (via BGP).
  3. Enables dynamic route propagation between on-prem, CloudGuard, and spoke VNets.
  4. Reduces the number of static UDRs needed over time.

Florida Branch Office Topology (≈100 sites)

Each branch is a small office hub-and-spoked back to Orlando, with Franklin as the backup. Branches register their subnets to a dedicated AD site so clients find the nearest DC and use the correct site link. Primary hosting for DHCP, RADIUS/NPS, and the WiFi controller is in Orlando, with Franklin as the standby.

 Connectivity
  • Site-to-site IPsec VPN — every branch, primary tunnel to Orlando, backup tunnel to Franklin.

Simplification Options & Transition Plan

 Collapse branch sites
Group low-population branches sharing a path into a few regional AD sites (e.g. North-FL, Central-FL, South-FL) instead of ~100 individual sites. Fewer connection objects, simpler KCC, slightly less precise DC locator.
 Site-link bridging on
If the WAN is fully routed (any-to-any), re-enable automatic bridging and let transitive costs handle pathing — drop most explicit bridges. Only keep manual control where you must force East-before-Central.
 Reduce RODC footprint
Replace branch RODCs with reliable dual VPN + cached logon where WAN is solid; keep RODCs only at high-latency or poorly-connected sites. Lowers patching and physical-security surface.
 SD-WAN + cloud breakout
An SD-WAN fabric (Orlando/Franklin as hubs) gives policy-based failover and lets branches break out to Azure directly, removing the hard dependency on Orlando for cloud access.

Transition Plan

Phase 1

Stabilize current hub-and-spoke

Register every branch subnet to its AD site; set primary/backup site links (Orlando primary, Franklin backup; inverse for North-FL). Stand up DHCP failover and NPS/WiFi standby in Franklin. Validate replication with the checks above before touching the cloud path.

Phase 2

Extend to Azure & lock topology direction

Add Azure-East and Azure-Central sites; create only Orlando/Franklin → East and East → Central links (no on-prem → Central). Confirm AZC replicates solely from AZE. This is the current target state of this design.

Phase 3

Introduce SD-WAN overlay (optional)

Deploy SD-WAN with Orlando/Franklin as hubs in monitor/standby mode alongside existing VPN/P2P. Validate failover and application steering without changing AD sites yet.

Phase 4

Cloud-direct branches & consolidation

Enable direct branch-to-Azure breakout over SD-WAN, optionally collapse branch sites into regional sites, and reduce RODCs. Re-evaluate whether Orlando must remain the sole aggregation hub or whether branches can reach cloud-hosted DCs directly as the migration scales.

  • Assign roles to groups, not individuals; scope to the smallest resource group that works; prefer custom roles over Owner when a built-in is too broad.
  • Vendors / 3rd party: B2B guest accounts, Conditional Access (MFA + compliant device), Reader by default, time-bound PIM, and quarterly access reviews — no standing access.
  • Cloud developers get Contributor only in non-prod; production changes flow through CI/CD with a service principal, not human Contributor.

 Use a synced (LDAP-mastered) group when…
  • Assigning Azure RBAC resource roles (Contributor, Reader, VM/Network/SQL Contributor) — fully supported.
  • Membership should stay governed by existing on-prem AD processes / joiner-mover-leaver.
  • The same group also gates on-prem resource access (single source of truth).
 Use a cloud-only group when…
  • Assigning Entra directory roles — requires a role-assignable (cloud-only) group; synced groups can't be flagged role-assignable.
  • Using PIM for Groups, dynamic membership, or self-service access you want governed in the cloud.
  • For Tier 0 / privileged access (keep these out of sync entirely).
Mapping caveats that bite
  • Role-assignable groups must be cloud-only — you cannot convert a synced group into a role-assignable group for Entra directory roles. Provision a separate cloud-only group for those.
  • Nested groups: Azure RBAC honors transitive (nested) membership, but Entra group-based app assignment and licensing do not — flatten membership for those use cases.
  • Dynamic membership rules only work on cloud-only groups, not synced ones.
  • Never sync built-in privileged groups (Domain Admins, Enterprise Admins, Account Operators) — exclude their OUs in Entra Connect; provision cloud-only equivalents per the cross-walk above.
  • Use global or universal security groups in AD for sync (domain-local groups don't sync usefully); apply OU/group-based filtering during pilot.
Group writeback (cloud → on-prem)

Where legacy on-prem apps must authorize against cloud-created groups, enable Entra Connect group writeback (v2) to write Microsoft 365 / security groups back into AD as on-prem groups. Use sparingly and govern naming — bidirectional group flow is easy to lose track of.

Detailed Steps: On-Prem File Server Migration (DFS-N / DFS-R)

File servers need special handling beyond a generic lift-and-shift because of DFS Namespaces (one server hosting multiple shares as folder targets), DFS-R replication relationships, NTFS/share ACLs, and the need to preserve the server identity so namespace referrals and mapped drives keep resolving after cutover. The current primary approach is a VM image-based migration with a Robocopy-based cutover; the methods below combine for different share types.

DFS Namespace & DFS-R Considerations

 DFS Namespaces (multi-share servers)
  • Domain-based (\\corp.local\dfs\…) and standalone (\\server\dfs\…) namespaces both reference share folder targets by server name.
  • If you preserve the hostname (rename target → source), all folder targets keep resolving with no DFS-N edits — this is the main reason the primary approach renames the target.
  • If the name changes, update each folder target with Set-DfsnFolderTarget / dfsutil and add the new target before removing the old.
 DFS-R replicated shares
  • For a DFS-R member, either pre-seed the target and re-establish replication, or add the Azure target as a new replication member, let it converge, then retire the old member.
  • Restoring a DFS-R member from image can cause a replication conflict / database mismatch — analogous to DC USN rollback. Do not let a stale DFSR database replicate authoritatively.
  • For large datasets, pre-seed with Robocopy then Export-DfsrClone / Import-DfsrClone to avoid a full initial sync; validate with dfsrdiag backlog.

Primary Approach — VM Image + Robocopy Cutover (current method)

  1. Provision the target VM in Azure via Azure Migrate (image-based migration of the source), or build a fresh File Server VM and re-create the File Server role, shares, and DFS configuration.
  2. Initial seed — Robocopy share data from source to target with full ACLs/owner/timestamps while the source stays live.
  3. Incremental passes — re-run Robocopy on a schedule to shrink the delta ahead of the cutover window.
  4. Final delta sync — during the maintenance window, run a last Robocopy pass to capture changes since the previous pass.
  5. Cutover identity swap — shut down the source server, then rename the target to the source's hostname, update DNS, and rejoin/reset the AD computer identity so SPNs, namespace targets, and mapped drives transfer transparently.
  6. Re-establish DFS — because the hostname is preserved, domain-based namespace targets and DFS-R memberships keep resolving; validate referrals and, if the image carried a stale DFSR database, re-seed / clone or perform a non-authoritative reinitialization.
  7. Validate — SMB access, share-level + NTFS permissions, DFS-N referrals, and DFS-R backlog; keep the source powered off but intact as a rollback point.
Secondary method: local user authentication for the final delta

Once the source has been renamed/removed from the domain during cutover, domain authentication for a last copy may fail. Run the final delta Robocopy using local administrator credentials on both ends (source temporarily isolated/renamed) as the fallback authentication path, then complete the identity swap on the target.

robocopy — seed, then delta (ACL-preserving)

  /TEE /LOG+:C:\MigLogs\seed.log

:: Incremental / final delta — same command re-run only moves changes

robocopy \\SRC\E$\Shares  E:\Shares /MIR /COPYALL /DCOPY:DAT /SECFIX /ZB /MT:32 /R:1 /W:1 /TEE /LOG+:C:\MigLogs\final.log

Rename-Computer -NewName "FILESRV01" -DomainCredential corp\migadmin -Restart

# Namespace targets resolve to the (preserved) server name

# Re-point a folder target only if the name changed
Set-DfsnFolderTarget -Path "\\corp.local\dfs\Data" -TargetPath "\\FILESRV01\Data" -State Online

dfsrdiag backlog /rgname:"Shares RG" /rfname:"Data" /smem:OLD-FILESRV /rmem:FILESRV01
dfsrdiag pollad

Detailed Steps: SQL Always On AG — Add Azure Replica & Migrate

Migrate a SQL Server Always On Availability Group with near-zero downtime by extending the existing WSFC into Azure: add an Azure VM as a new replica, seed the database through AG replication, let it synchronize, then fail over to the Azure replica and retire the on-prem replicas. The on-prem and Azure nodes form a multi-subnet stretched cluster, so the listener needs an Azure Internal Load Balancer and the DNS TTLs must be tuned for fast client re-resolution at failover.

AD & Cluster permissions (do these first)
  • Cluster Name Object (CNO) must be able to create the listener's Virtual Computer Object (VCO): grant the CNO computer account Create Computer objects + Read all properties on the cluster OU, or pre-stage the VCO and grant the CNO Full Control over it.
  • The engineer running Add-ClusterNode needs local administrator on all nodes and Create Computer objects in the target OU.
  • New node's computer account joined to corp.local and placed in the correct OU / AD site (Azure-East).
  • SQL service accounts added as logins on every replica, and granted CONNECT on the database-mirroring endpoint (port 5022).
  • For TDE-encrypted DBs, export the server certificate + private key from the source and import on the Azure replica before seeding.

1 · Pre-flight parity check

  • SQL version, edition, CU/patch level, and collation on the Azure replica must match the source.
  • Same Windows Server version/patch level and Failover Clustering feature.
  • Transfer server-level objects: logins (with SIDs), SQL Agent jobs, linked servers, credentials, endpoints, certificates.
  • Verify ExpressRoute connectivity and that AD/DNS resolve across sites.

2 · Provision the target Azure VM

  • Right-size the VM (memory-optimized series); enable accelerated networking; use Premium SSD v2 / Ultra disks with separate disks for data, log, and tempdb.
  • Join to corp.local (Azure-East AD site); install the Failover Clustering feature and SQL Server (matching version/CU) with the same service accounts.
  • Enable Always On AG in SQL Server Configuration Manager (requires the node to be a cluster member first — see step 4).

2b · Alternative — image a secondary node (Azure Migrate, OS volume only)

Instead of building the VM from scratch, clone an existing secondary replica node to guarantee OS/driver/patch parity, then strip its cluster and SQL identity and rebuild SQL cleanly from the original install answer file. Image a secondary (never the primary) so production isn't disturbed and no live database data is copied.

  1. Replicate with Azure Migrate — OS volume only. Add the source secondary node to Azure Migrate and, in disk selection, replicate only the OS disk; deselect the data, log, and tempdb data drives. This carries the Windows build, Failover Clustering feature, SQL prerequisites, and config — without any database volumes.
  2. Provision fresh data disks. On the migrated target, attach new empty managed disks for data / log / tempdb and format them with the same drive letters / mount points the original build (and the INI) expect, so install paths resolve and AG seeding has somewhere to land.
  3. Clean the cluster identity. The clone still carries the source cluster's metadata — wipe it before it can rejoin or conflict.
  4. Rename & rejoin the domain. A clone shares the source computer name; rename it and rejoin corp.local (new identity, correct OU / Azure-East site) before re-clustering.
  5. Reinstall SQL from the preserved answer file. Remove the cloned instance registration and reinstall using the ConfigurationFile.ini saved from the original cluster build, so instance name, features, directories, collation, and service accounts match exactly.

Azure doesn't support the floating ARP that a normal AG listener VIP relies on, so the listener IP in the Azure subnet is fronted by a Standard ILB with a health probe. The listener becomes multi-subnet: one IP on-prem, one in Azure.

  • Create a Standard ILB: frontend IP = listener VIP in the Azure SQL subnet (e.g. 10.11.5.20); backend pool = the SQL node(s); health probe TCP 59999; LB rule for 1433 (and 5022) with Floating IP (DSR) enabled.
  • Add the Azure IP to the AG listener, then set the cluster IP resource's probe port and a /32 mask so the ILB can health-check the active node.

7 · DNS TTL adjustments (fast client re-resolution)

A multi-subnet listener registers an IP per subnet. Lower the listener's HostRecordTTL so clients re-resolve quickly after failover, keep RegisterAllProvidersIP on for modern drivers, and have applications connect with MultiSubnetFailover=True.

powershell — listener DNS behavior
# Lower TTL from the 1200s default to 300s (or 60s) for quick failover re-resolve

Get-ClusterResource "AGL-Prod" | Set-ClusterParameter -Name RegisterAllProvidersIP -Value 1

# Restart the listener for the change to take effect
Stop-ClusterResource "AGL-Prod"; Start-ClusterResource "AGL-Prod"

Legacy clients

If older drivers can't use MultiSubnetFailover, set RegisterAllProvidersIP=0 and rely on the low HostRecordTTL so the single active listener IP propagates quickly — but expect a TTL-bounded reconnect delay at failover.

8 · Cutover & cleanup

  1. Confirm the Azure replica is healthy and caught up (sys.dm_hadr_database_replica_states — SYNCHRONIZING/low send-queue).
  2. Briefly switch the Azure replica to synchronous commit and wait for SYNCHRONIZED.
  3. During the maintenance window, perform a manual failover to the Azure replica; validate app connectivity through the listener.
  4. Give the Azure node a quorum vote; move the Cloud Witness role as appropriate; re-confirm quorum.
  5. Once stable, remove the on-prem replicas from the AG and evict the on-prem nodes from the cluster; remove their listener IP.
Validation & rollback

Validate: listener resolves to the Azure IP, apps reconnect within the TTL window, AG dashboard healthy, jobs/logins present. Keep the on-prem replicas in the AG (async) as a rollback target until the Azure replica has run clean through a full business cycle — failback is a manual failover in reverse.

Appendix · Carbon Black Exclusions for Azure Agents

Endpoint Security

VMware Carbon Black can break the Azure migration/DR agents in two ways: by blocking the Mobility service kernel filter driver from loading (replication stops) and by flagging or throttling the high-volume disk reads the agents perform during replication and backup. These exclusions let the agents for Azure Migrate, Azure Backup (MARS), and Azure Site Recovery run without being quarantined or starved.

Scope & safety

Exclude only the specific agent paths, processes, and drivers below — never disable the sensor or exclude broad roots like C:\. Scope path rules as tightly as your Carbon Black product allows, and re-validate after every agent upgrade (paths and binaries change between versions).

How the exclusions map to your Carbon Black product

 Carbon Black Cloud (Endpoint Standard / EDR)
Add path-based Permissions rules in the assigned policy. For each agent path, set the operation attempt to "Performs any operation" → Bypass so the sensor stops inspecting that process's behavior and I/O. Pair with reputation allow-listing where available.
 Carbon Black App Control (CB Protection)
Application allow-listing: Approve the agent binaries (by path, publisher, or hash) and explicitly approve the kernel driver so it can load. Add custom Allow rules for the scratch/cache write paths so the agents can write freely.
The two items that most often break things
  • Mobility service volume filter driver (e.g. involflt.sys) — used by Azure Migrate agent-based replication and ASR to track disk writes. App Control will block an unapproved driver from loading, which silently halts replication. Approve the driver.
  • cbengine.exe (MARS backup engine) — reads every file during backup; EDR can interpret this as mass file access and throttle or alert. Bypass the process and its scratch/bin folders.
Azure Migrate (server migration)

Agentless replication runs from the appliance; agent-based replication installs the Mobility service on the source VM (same components as ASR).

Appendix · Network Capture & Dependency Mapping

Discovery

Before moving a workload you need to know who connects to it. This workflow captures traffic on a server with built-in Windows ETL tracing, converts it to a Wireshark-readable .pcapng, then correlates the server's listening services (from netstat -ano) with the initiators seen in the capture — producing a per-service client list that drives migration move-groups, boot order, and NSG/firewall validation.

 Capture — Windows ETL trace
netsh trace (all Windows) / pktmon (2019+)
:: Option A — netsh trace (NDIS packet capture to .etl)
netsh trace start capture=yes report=disabled maxSize=2048 ^
  tracefile=C:\caps\dbsrv.etl
:: ...let it run over a representative business window, then:
netsh trace stop

:: Option B — pktmon (Windows Server 2019+); full packets
pktmon start --capture --pkt-size 0 --file-name C:\caps\dbsrv.etl
:: ...reproduce/observe traffic, then:
pktmon stop
 Convert ETL → PCAPNG
etl2pcapng (or pktmon native)
:: Microsoft etl2pcapng (github.com/microsoft/etl2pcapng)
etl2pcapng.exe C:\caps\dbsrv.etl C:\caps\dbsrv.pcapng

:: Alternative — pktmon converts natively
pktmon pcapng C:\caps\dbsrv.etl -o C:\caps\dbsrv.pcapng
 Find listening services — netstat -ano
listening sockets → PID → process
:: All listeners with owning PID
netstat -ano | findstr LISTENING

:: Narrow to the SQL service: shows local IP:port and PID
netstat -ano | findstr :1433
::   e.g.  TCP   10.11.0.20:1433   0.0.0.0:0   LISTENING   4820

:: Map the PID to the process
tasklist /fi "PID eq 4820"          ::  ->  sqlservr.exe
:: PowerShell equivalent that joins port + process in one shot:
Get-NetTCPConnection -State Listen | Select LocalAddress,LocalPort,OwningProcess,@{n='Proc';e={(Get-Process -Id $_.OwningProcess).ProcessName}}

 Correlate — find the initiators (clients) of a target service

The netstat output gives the listening target (IP, port, PID). In the capture, the initiator of each TCP session is the side that sends the opening SYN (syn==1, ack==0) toward that port — those source IPs are the clients that depend on the service.

tshark — DB server example (target 10.11.0.20:1433)
# Every client that OPENED a connection to the SQL service (SYN to dstport 1433)
tshark -r dbsrv.pcapng \
  -Y "tcp.dstport==1433 && ip.dst==10.11.0.20 && tcp.flags.syn==1 && tcp.flags.ack==0" \
  -T fields -e ip.src -e tcp.srcport \
  | sort -u

# Count connections per client (rank the heaviest dependents)
tshark -r dbsrv.pcapng \
  -Y "tcp.dstport==1433 && ip.dst==10.11.0.20 && tcp.flags.syn==1 && tcp.flags.ack==0" \
  -T fields -e ip.src | sort | uniq -c | sort -rn
Output → migration action

The unique ip.src list is the dependency map for that service: every app/web/jump server that must move with (or retain connectivity to) the database. Use it to build move-groups and boot order, and to confirm the Section 12 NSG allow-rules match the clients you actually observe — anything connecting that isn't in the rule set is a gap; any rule with no observed traffic is a candidate to remove.

Capture practicalities
  • Run the capture across a representative window (include nightly jobs, backups, batch) — a 5-minute trace misses periodic dependents.
  • netsh trace / pktmon capture at the NDIS layer and can grow fast; cap maxSize or use circular mode, and capture to a non-system disk.
  • Payloads inside TLS aren't decrypted — this workflow maps connections, not content, which is exactly what dependency mapping needs.
  • Capture on the target service host for completeness; capturing on a client only shows that client's flows.

Best production path — Tampa → Orlando → US East 2
Tampa 10 ms + Orlando→East2 32 ms + hub 2 ms = ~44 ms RTT

Tampa 10 ms + Orlando→Central 56 ms + hub 2 ms = ~68 ms RTT  (+24 ms vs primary)

Reading the budget
  • Primary path holds up: Tampa→Orlando→US East 2 (~44 ms) and Miami→Orlando→US East 2 (~52 ms) are comfortably inside the <100 ms range where interactive apps feel responsive.
  • DR adds ~20–24 ms: routing the same users to US Central costs roughly +24 ms — acceptable for a failover scenario, not ideal as steady state.
  • Franklin hub-failover adds ~15–20 ms over the Orlando path for southern cities — usable as a backup but confirms Orlando-primary is the right default.
  • Replication is latency-tolerant: these RTTs matter for interactive user sessions; async AD/file replication and ASR care about throughput and RPO, not these single-digit-to-tens-of-ms differences.
How to measure the real numbers
  • Azure Network Watcher → Connection Monitor: agent-based, continuous RTT/loss between on-prem probes and Azure VMs across both regions.
  • psping -n 100 <dc-or-vm-ip>:<port> for TCP-handshake RTT (ICMP is often deprioritized/blocked).
  • pathping <ip> for per-hop latency/loss across the VPN and Megaport circuit.
  • Probe from real branch endpoints (Tampa/Miami offices), not just the datacenter, to capture the true last-mile.

Chargeback vs Showback

 Showback
Report cost per app / business unit for visibility and accountability — no internal money moves. Start here: build Cost Management views grouped by Application, CostCenter, and Environment.
 Chargeback
Actually bill internal cost centers for their consumption. Requires clean, enforced tags and an agreed method for splitting shared platform costs (below). Graduate to this once showback is trusted.
Allocating shared platform costs

The always-on platform (ExpressRoute/Megaport, the four DCs, CloudGuard NVA, Bastion, Log Analytics/Sentinel) isn't owned by one app. Allocate it across consumers with Azure Cost Management cost-allocation rules — distribute by the AllocationPct tag, by proportional compute spend, or evenly across business units — so chargeback reflects true total cost, not just direct resources.

Enforcement & Governance

  • Inherit environment/owner/cost tags from the resource group via Azure Policy so individual resources don't have to be tagged by hand.
  • Require the core tags with a deny/audit policy; append missing tags with a modify policy during deployment.
  • Apply tags in IaC (Bicep/Terraform) as the source of truth; let policy backstop drift.
  • Standardize on PascalCase keys and a controlled value list — tag keys are case-insensitive for billing grouping but values are case-sensitive, so Prod ≠ prod in reports.

Limits & practical notes
  • Max 50 tags per resource; key ≤ 512 chars, value ≤ 256 chars. Keep the required set small and high-value.
  • Tags are not inherited by child resources by default — use the inherit policy, and note a few resource types don't support tags.
  • CostCenter, Application, and Environment are the three that most reports and chargeback rules pivot on — enforce these hardest.
  • Export tagged cost data from Cost Management to a storage account for finance, and reconcile monthly.

 Linking to the CMDB — ServiceNow Discovery for Azure

The tags above aren't just for cost — they're the glue that ties Azure resources to the ServiceNow CMDB. ServiceNow Discovery (via the Service Graph Connector for Microsoft Azure) inventories the Azure estate into Configuration Items (CIs), carries the tags across as CI attributes, and lets you build Application Services and link incidents/changes/problems to the exact resources they affect.

Discovery flow
ServiceNow ↔ Azure
ServiceNow instance → MID Server → Azure Resource Manager APIs (via Entra service principal, Reader) → resource inventory + tags
Reconcile
Inventory → Identification & Reconciliation Engine (IRE) → de-duped CIs in the CMDB (CSDM classes)
Map & link
Tags → CI attributes → Application Services (grouped by Application/AppID) → Incidents / Changes / Problems linked to CIs

Setup

  1. Plugins: enable the Service Graph Connector for Microsoft Azure (or Cloud Discovery), Discovery, CMDB/CSDM, and optionally Service Mapping in the ServiceNow instance.
  2. MID Server: deploy a MID Server (on-prem or an Azure VM in a spoke) with outbound HTTPS to Azure ARM and to the ServiceNow instance.
  3. Azure app registration: register an Entra ID application, create a client secret or certificate, and grant it the Reader role at the management group or per-subscription scope. Record tenant, client, and subscription IDs.
  4. Configure the connector: in ServiceNow, enter the credentials and MID Server, select the in-scope subscriptions/regions, and map data sources.
  5. Schedule: run discovery/ETL on a recurring schedule (e.g. daily) so the CMDB stays current; IRE reconciles against existing CIs.
Least-privilege & credential handling

Discovery needs read-only access — grant Reader only, never Contributor. Scope it at a management group so new subscriptions are covered automatically. Store the client secret/certificate in Key Vault (or ServiceNow's credential store), rotate it, and never embed it in scripts.

 Application Services
Group the discovered CIs into an Application Service using tag-based service mapping on the Application/AppID tag (or Service Mapping for dependency-aware maps). Linking tickets & incidents to CIs
  • Incidents, changes, and problems reference the Affected CI and its Application Service — giving impact analysis and a single view of everything touching an app.
  • The SupportTeam/OnCall tags auto-route tickets to the right assignment group; Criticality sets priority/SLA.
  • Monitoring alerts (Azure Monitor / Sentinel) can create ServiceNow incidents pre-linked to the CI via the resource ID, closing the loop from detection to ticket to the exact Azure resource.
  • Validate after each run: reconciliation has no duplicate CIs, Application Services list their members, and stale CIs age out on schedule.
