GCP Cloud DNS Forwarding Integration

Forwarding Zones • DNS Policies • Exclusive Switching • TTL Optimized
SECTION DETAILED STEPS / CONTENT
1. Workshop Objective
Review and validate integration of GCP Cloud DNS forwarding zones and DNS policies with the shared DNS VPC (192.168.30.0/24) to support exclusive, switchable operation between BlueCat (anycast VIP 10.100.100.100) and EfficientIP (anycast VIP 192.168.153.153). Ensure seamless resolution for corp.pri. and mcd.cloud. domains. Azure clients remain in Azure VNets; DNS solutions run in GCP. GCP workloads and Azure clients must resolve via either VIP over Equinix Fabric BGP.
2. Architecture Constraints
  • BlueCat MDDS + Edge Resolver and EfficientIP run in parallel in the same GCP DNS VPC (192.168.30.0/24).
  • Anycast VIPs are unique per solution and advertised via FRR/BGP + Cloud Router to Equinix Fabric.
  • GCP has no per-VPC resolver limit; use Cloud DNS forwarding zones (conditional) or DNS policies (VPC-wide alternative name servers).
  • Azure client VNets remain in Azure; reachability to GCP VIP occurs over Equinix Fabric private IP-WAN (ExpressRoute / Direct Connect equivalent).
  • GCP workloads use the same VIP via forwarding zones or DNS policies applied to their VPCs.
  • Platforms will not run simultaneously; switch exclusively between BlueCat and EfficientIP.
3. Cloud DNS Forwarding / Policy Deployment
Deploy a forwarding zone (conditional) or DNS policy (VPC-wide) that forwards corp.pri. and mcd.cloud. to the active anycast VIP.

One-time gcloud commands (initial BlueCat active):
gcloud dns managed-zones create ruleset-corp \
  --dns-name=corp.pri. \
  --visibility=private \
  --networks=vpc-dns-spoke-us-east4 \
  --forwarding-targets=10.100.100.100

gcloud dns managed-zones create mcd-cloud-rule \
  --dns-name=mcd.cloud. \
  --visibility=private \
  --networks=vpc-dns-spoke-us-east4 \
  --forwarding-targets=10.100.100.100

# Alternative VPC-wide policy (recommended for all queries)
gcloud dns policies create ruleset-corp-policy \
  --networks=vpc-dns-spoke-us-east4 \
  --alternative-name-servers=10.100.100.100 \
  --description="Corp DNS forwarding to active anycast VIP"
4. DNS Forwarding Ruleset / Policy Configuration
Single ruleset/policy forwards both domains to the active anycast VIP only.

Initial creation (BlueCat active) – already shown above.
5. Platform Switching Procedure
Switch to EfficientIP:
gcloud dns managed-zones update ruleset-corp \
  --forwarding-targets=192.168.153.153

gcloud dns managed-zones update mcd-cloud-rule \
  --forwarding-targets=192.168.153.153

# Or for DNS policy (VPC-wide)
gcloud dns policies update ruleset-corp-policy \
  --alternative-name-servers=192.168.153.153
Switch back to BlueCat: reverse the IPs above.

Alternative non-disruptive method: Delete and re-create the forwarding zones/policy with the new target VIP.
6. Client Configuration (GCP workloads + Azure clients)
GCP workloads (us-east4 VPCs): Apply the forwarding zones or DNS policy to the target VPC(s).
gcloud dns policies update ruleset-corp-policy \
  --networks=vpc-workload-us-east4,vpc-other-workload
Azure clients (stay in Azure): Point VNet DNS servers to the global anycast VIP (routed via Equinix Fabric).
# BlueCat active
az network vnet update --resource-group <client-rg> --name vnet-client-eastus --dns-servers 10.100.100.100

# EfficientIP active (switch)
az network vnet update --resource-group <client-rg> --name vnet-client-eastus --dns-servers 192.168.153.153
Existing Azure VMs require ipconfig /release && ipconfig /renew.
7. Cloud DNS Caching Behavior
  • Cloud DNS caches responses from the upstream anycast VIP according to the exact TTL returned by BlueCat Edge Resolver or EfficientIP.
  • Forwarding zone / policy changes take effect for new queries immediately, but cached entries persist until TTL expiry.
  • Azure client VMs and GCP instances also cache per-record TTLs.
8. Cache Flush Limitations
Cloud DNS has no direct flush API.

Workarounds (in order of preference):
  1. Low TTLs (60–300 s) on zones during POC.
  2. Delete/re-create forwarding zones or update DNS policy (forces re-evaluation).
  3. Client-side: ipconfig /flushdns (Windows) or systemd-resolve --flush-caches (Linux).
  4. Nuclear option: recreate the entire policy/zone (minimal disruption).
9. DNS TTL Optimization Strategies
(Identical table as Azure guide – POC: 60–300 s, Cutover: 60 s, Production: 300–1800 s, Global Anycast VIP: 60 s)
10. Operational Runbook Summary & Recommendations
  • Pre-cutover: lower TTLs + update forwarding zones/policy + Azure VNet DNS + GCP workload networks.
  • Post-cutover: wait one TTL cycle + force client flush.
  • Monitor with dig @10.100.100.100 or dig @192.168.153.153 from Azure and GCP test VMs.
  • All changes maintain single-engineer execution and global anycast VIP behavior across Equinix Fabric.
