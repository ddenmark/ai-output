Google Cloud DNS Forwarding Integration

Forwarding Zones • DNS Policies • Exclusive Switching • TTL Optimized
SECTION DETAILED STEPS / CONTENT
1. Workshop Objective
Validate Google Cloud DNS integration with the shared DNS VPC (192.168.30.0/24) for exclusive, switchable operation between BlueCat anycast VIP (10.100.100.100) and EfficientIP anycast VIP (192.168.153.153). Azure clients remain in Azure VNets; GCP workloads and intra-VPC test VMs use native Google Cloud DNS forwarding zones and policies.
2. Google Cloud DNS Concepts
Google Cloud DNS is a scalable, managed DNS service offering authoritative and recursive resolution. For private/internal DNS in this POC:
  • Forwarding Zones (Conditional Forwarding): Private managed zones that forward specific domains (corp.pri., mcd.cloud.) to upstream anycast VIPs. Recommended for granular control.
  • DNS Policies (VPC-wide Alternative Name Servers): Apply alternative name servers to one or more VPCs for all queries. Simpler for POC-wide consistency.
  • Caching follows exact TTL from upstream (BlueCat Edge or EfficientIP). Changes to zones/policies are immediate for new queries.
  • Reachability: Azure clients reach VIPs via Equinix Fabric private IP-WAN. GCP workloads resolve natively within the same or peered VPCs.
Recommendation for POC: Use forwarding zones for precision; fall back to DNS policies for simplicity across all GCP workloads.
3. Architecture Constraints
  • DNS appliances run in parallel in the DNS VPC (192.168.30.0/24); VIPs advertised via Cloud Router + FRR/BGP to Equinix Fabric.
  • Azure client VNets stay in Azure; no direct VPC peering required.
  • GCP workloads in the same VPC (different subnet) or peered VPCs use Google Cloud DNS forwarding/policy.
  • Switching is exclusive; platforms do not run simultaneously.
4. Google Cloud DNS Forwarding / Policy Deployment
One-time gcloud commands (BlueCat active):
gcloud dns managed-zones create corp-pri-forward \
  --dns-name=corp.pri. --visibility=private \
  --networks=vpc-dns-spoke-us-east4 \
  --forwarding-targets=10.100.100.100

gcloud dns managed-zones create mcd-cloud-forward \
  --dns-name=mcd.cloud. --visibility=private \
  --networks=vpc-dns-spoke-us-east4 \
  --forwarding-targets=10.100.100.100

# Optional VPC-wide DNS Policy
gcloud dns policies create ruleset-corp-policy \
  --networks=vpc-dns-spoke-us-east4 \
  --alternative-name-servers=10.100.100.100
5. Platform Switching Procedure
Switch to EfficientIP: 
gcloud dns managed-zones update corp-pri-forward --forwarding-targets=192.168.153.153
gcloud dns managed-zones update mcd-cloud-forward --forwarding-targets=192.168.153.153
# For policy: gcloud dns policies update ruleset-corp-policy --alternative-name-servers=192.168.153.153
Reverse IPs to switch back. Alternative: delete/re-create zones.
6. Client Configuration
GCP workloads: Apply zones/policy to target VPCs.
Azure clients: Update VNet DNS servers to active VIP (routed via Equinix Fabric).
7. Testing Scenario: Windows Server in DNS VPC (different subnet)
Deploy a Windows Server 2022/2025 VM in the DNS VPC (e.g., subnet 192.168.31.0/24).
Steps:
  1. Create VM; join to corp.root domain.
  2. Set DNS: netsh interface ip set dns "Ethernet" static 10.100.100.100 (BlueCat) or 192.168.153.153 (EfficientIP).
  3. Test: nslookup www.example.com 10.100.100.100 and domain queries.
  4. Switch platform and re-test after TTL expiry + ipconfig /flushdns.
8. Google Cloud DNS Troubleshooting
Key Diagnostic Commands: 
gcloud dns managed-zones list
gcloud dns managed-zones describe corp-pri-forward
gcloud dns policies describe ruleset-corp-policy
gcloud compute routers describe cr-bluecat --region=us-east4
gcloud compute routers get-status cr-bluecat --region=us-east4 --format="table(bgpPeers[])"
Common Issues & Resolution:
  1. Forwarding zone/policy not resolving: Verify attachment to correct VPC and target VIP; re-create if needed.
  2. BGP reachability: Confirm Cloud Router peers are Established and VIP is advertised.
  3. Azure clients unreachable: Validate Equinix Fabric BGP and connectivity; test port 53 from Azure VM.
  4. Stale cache after switch: Wait TTL cycle or run ipconfig /flushdns.
  5. Intra-VPC Windows VM fails: Confirm same-VPC subnet, static/DHCP DNS, and firewall rules (UDP/TCP 53).

Logging: Enable Cloud DNS query logging or use VPC Flow Logs / Cloud Logging.
9. Google Cloud DNS Caching Behavior Caches per exact TTL from upstream. Changes immediate for new queries.
10. Cache Flush Limitations & Workarounds No direct flush; use low TTLs, delete/re-create zones/policy, or client flush.

12. Operational Runbook Summary Pre-cutover: lower TTLs + update zones/policy. Post-cutover: wait TTL cycle + flush. Monitor with dig/nslookup from Azure and GCP test VM.
