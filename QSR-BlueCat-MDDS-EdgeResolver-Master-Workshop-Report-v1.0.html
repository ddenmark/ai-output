Architecture Overview

This POC validates BlueCat MDDS as a Tier 0 hidden primary master hosted in Equinix, paired with BlueCat Edge Resolver Service Point v4 HA pairs deployed across all three cloud providers. All Edge Resolvers advertise a shared Anycast VIP via FRR/BGP over the Equinix Fabric IP-WAN, enabling nearest-server routing for 48,000+ restaurants globally. CORP and Market entities remain strictly isolated per architecture policy.

TIER 0 — HIDDEN MASTER
BlueCat MDDS · Equinix Colo
Single MDDS instance hosted in the Equinix facility serving as the authoritative hidden primary for all CORP zones (corp.pri, mcd.cloud, reverse zones). Never directly reachable by clients. TSIG-secured zone transfers to all Tier 1+2 Edge Resolvers. Managed via Micetro Central.
TIER 1+2 — EDGE RESOLVERS
BlueCat Edge v4 · HA Pairs per Cloud
Two Edge Resolver VMs per cloud (Azure, AWS, GCP) combine authoritative and recursive resolution in a single appliance. Each VM holds a secondary IP configured as the Anycast VIP (10.100.100.100/32), advertised via FRR/BGP to the Equinix Fabric Cloud Router. Anycast ensures closest-node routing globally.
CONTROL PLANE
Micetro Central + Equinix Fabric BGP
Micetro Central (DDI orchestration) manages all servers centrally with LDAP/AD-integrated RBAC. Equinix Fabric Cloud Router (ASN 65000) peers with all six Edge VMs (local ASN 64512). BGP health-based withdrawal removes unhealthy nodes from routing automatically within ≤5s convergence.

Phase 5
Health-Based BGP Withdrawal (All Edge Resolvers)

Deploy this script on all six Edge Resolvers as a systemd timer. It withdraws the Anycast VIP from BGP if local DNS is unhealthy, and re-advertises when recovered.

# /usr/local/bin/bc-dns-health-check.sh
#!/bin/bash
PROBE_DOMAIN="corp.pri"
VIP="10.100.100.100/32"
ECS_VIP="10.100.100.102/32"

if dig @127.0.0.1 SOA "${PROBE_DOMAIN}" +short +time=3 +tries=2 > /dev/null 2>&1; then
  # DNS healthy — ensure VIPs are advertised
  vtysh -c "configure terminal" -c "router bgp 64512" \
        -c "address-family ipv4 unicast" \
        -c "network ${VIP}" \
        -c "network ${ECS_VIP}" \
        -c "end" -c "write"
  logger -t bc-health "DNS healthy — VIPs advertised"
else
  # DNS unhealthy — withdraw VIPs from BGP
  vtysh -c "configure terminal" -c "router bgp 64512" \
        -c "address-family ipv4 unicast" \
        -c "no network ${VIP}" \
        -c "no network ${ECS_VIP}" \
        -c "end" -c "write"
  logger -t bc-health "DNS unhealthy — VIPs WITHDRAWN"
fi
# /etc/systemd/system/bc-dns-health.timer
[Unit]
Description=BlueCat DNS Health Check & BGP VIP Manager

[Timer]
OnBootSec=60
OnUnitActiveSec=30s

[Install]
WantedBy=multi-user.target
sudo chmod +x /usr/local/bin/bc-dns-health-check.sh
sudo systemctl enable bc-dns-health.timer
sudo systemctl start bc-dns-health.timer

BGP-01 Equal-Cost Anycast — Nearest Node Resolution Basic

Objective: Confirm that clients in each cloud region resolve DNS via their topologically nearest Edge Resolver, and that all six nodes are advertising the VIP equally.

  • From test client in Azure East US 2 VNet: dig @10.100.100.100 portal.corp.pri +short — expected: response from edge-bc-az-eus2-01 or -02 (verify via query logs).
  • From test client in AWS us-east-2: same dig — expected: response from edge-bc-aws-use2-01 or -02.
  • From test client in GCP us-east4: same dig — expected: response from edge-bc-gcp-use4-01 or -02.
  • Confirm all 6 nodes show Established: for host in 192.168.16.20 192.168.16.21 192.168.20.20 192.168.20.21 192.168.30.20 192.168.30.21; do ssh bluecat@$host "vtysh -c 'show ip bgp summary' | grep -E 'Neighbor|Estab'"; done
  • Expected Result: Each cloud's clients prefer their local nodes. BGP summary shows 6 unique paths to 10.100.100.100/32 in Equinix route table.
BGP-02 Single Node Failure — FRR Stop & Convergence Timing Failover

Objective: Validate sub-5-second convergence when one Edge Resolver is taken offline. Client queries must continue resolving during the event.

  • Start continuous DNS probe from Azure test client: while true; do dig @10.100.100.100 portal.corp.pri +short; sleep 0.5; done
  • SSH to edge-bc-az-eus2-01.corp.pri and stop FRR: sudo systemctl stop frr
  • Observe: probe client experiences ≤5s gap or zero interruption (BGP hold-timer = 90s, but health script fires every 30s — confirm health-script withdrawal fires faster). Timer should withdraw VIP within 30s of DNS failure, BGP within hold-timer.
  • Restore: sudo systemctl start frr — confirm VIP re-advertised: vtysh -c "show ip bgp 10.100.100.100"
  • Success Criteria: DNS resolution never returns SERVFAIL for more than 5 consecutive seconds. Syslog shows bc-health: DNS unhealthy — VIPs WITHDRAWN.
BGP-03 AS-Path Prepending — Traffic Engineering per Cloud Traffic Engineering

Objective: Validate the Azure → AWS → GCP preference hierarchy using AS-path prepending. Confirm traffic shifts predictably when preference changes.

BGP-04 Full Cloud Withdrawal — Azure CSP Outage Simulation Disaster Recovery

Objective: Simulate complete Azure CSP outage. Both Azure Edge Resolvers stop advertising. Confirm full traffic failover to AWS and GCP with no DNS outage for 48,000+ restaurants.

  • Run continuous probes from multiple test clients (Azure, AWS, GCP, simulated WAN client).
  • Stop FRR on both Azure nodes simultaneously:
    for h in 192.168.16.20 192.168.16.21; do ssh bluecat@$h "sudo systemctl stop frr" & done; wait

  • Confirm AWS and GCP paths remain: clients continue resolving. No SERVFAIL observed.
  • Re-enable Azure: for h in 192.168.16.20 192.168.16.21; do ssh bluecat@$h "sudo systemctl start frr"; done — confirm paths return within BGP hold-timer.
  • Success Criteria: Zero DNS outage during full Azure failure. Convergence to AWS/GCP in ≤90s (hold-timer). Return of Azure paths in ≤5 min.
BGP-05 Health-Based Auto-Withdrawal — DNS Service Failure Automation

Objective: Confirm the health-check script automatically withdraws the anycast VIP when the local DNS daemon fails, without any manual intervention.

  • On edge-bc-gcp-use4-01, simulate DNS failure (stop the Edge Resolver service, not FRR): consult BlueCat Edge admin guide for service stop procedure.
  • Within 30s (health timer interval), observe journalctl -f -t bc-health showing DNS unhealthy — VIPs WITHDRAWN.
  • FRR peer remains connected but no network 10.100.100.100/32 is applied — confirm with vtysh -c "show ip bgp 10.100.100.100" — local VIP should no longer be in the BGP table.
  • Restore Edge Resolver service. Within the next 30s health check cycle, VIP is re-advertised automatically.
  • Success Criteria: Withdrawal fires within 30s of DNS failure. Re-advertisement fires within 30s of DNS recovery. No human intervention required.

Objective: Validate that the REGIONAL-ECS VIP (10.100.100.102/32) provides EDNS Client Subnet-aware responses that direct Market tenant workloads to region-appropriate endpoints.

  • Simulate EMEA client: dig @10.100.100.102 portal.corp.pri +subnet=10.201.0.1/24 — confirm EMEA endpoint returned.
  • Confirm Market tenant isolation: EMEA Market zone records must not be returned to NA Market client queries and vice versa.
  • Verify ECS is enabled on all 6 Edge Resolvers in Micetro Central: DNS → Resolver → Advanced → Client Subnet Support = Enabled.
  • Success Criteria: ECS responses vary by subnet prefix. Market zone records remain isolated. No cross-market zone leakage.
BGP-07 Phased Rollout — Community-Based Market Scoping Migration

Objective: Validate blast-radius control during phased migration from AD DNS to BlueCat. Enable BlueCat anycast only for NA Market first, while other markets remain on legacy DNS.

  • Add community tag to NA-only advertisement on all Edge Resolvers:
    vtysh -c "conf t" -c "route-map ANYCAST-OUT permit 10" -c "set community 64512:100 64512:NA additive" -c "end"
  • Coordinate with network team: configure Equinix to only propagate the 10.100.100.100/32 prefix to NA Market VRF. Other market VRFs continue pointing to legacy AD DNS IPs.
  • DHCP option 6 in NA Market scopes: update to 10.100.100.100. Other market scopes: retain legacy DNS IPs.
  • Validate: NA Market clients resolve via BlueCat. EMEA/APAC/LATAM clients still reach legacy AD DNS. Monitor both for 72 hours before expanding.
  • Success Criteria: Zero resolution failures in NA Market. Zero impact to other markets. Rollback path: revert DHCP option 6 to legacy IPs.
BGP-08 Rollback — Emergency Reversion to Legacy AD DNS Rollback

Objective: Execute and time a full emergency rollback from BlueCat anycast to legacy Microsoft AD DNS within SLA (target: ≤15 minutes).

  • Revert DHCP option 6 in all market scopes to legacy AD DNS IPs (pre-prepared runbook). In Azure: Portal → VNet DNS → switch back to DC IPs. In AWS: DHCP Options Set revert. In GCP: VPC DNS settings revert.
  • As clients renew DHCP leases (or forced renew), they return to AD DNS. Force renew on test clients: Windows: ipconfig /release && ipconfig /renew. Linux: dhclient -r && dhclient.
  • Optionally stop FRR on all Edge Resolvers to immediately withdraw the anycast VIP from BGP (belt-and-suspenders).
  • Verify with AD DC: dig @192.168.16.50 portal.corp.pri returns records. Client DNS shows legacy AD DC IPs.
  • Success Criteria: All clients resolve via AD DNS within 15 minutes of rollback initiation. BlueCat Edge Resolvers can remain online for monitoring without serving client traffic.
BGP-09 Rate Limiting & DNS DDoS Protection Security

Objective: Validate that BlueCat Edge Resolvers enforce DNS rate limiting to protect against amplification attacks and query flooding across the 48,000-restaurant footprint.

  • Configure rate limiting in BlueCat Edge Resolver admin UI: DNS → Rate Limiting → set per-client limit (e.g., 100 QPS per source IP) and global limit.
  • Run DNS flood from test client: dnsperf -s 10.100.100.100 -d queryfile.txt -Q 500 -l 30 (requires dnsperf tool).
  • Confirm: responses from Edge Resolver drop to configured rate limit. SERVFAIL or REFUSED returned for excess queries. Legitimate queries from other clients are unaffected.
  • Verify rate-limit logs in Micetro Central: Monitoring → DNS Rate Limit Events.
  • Success Criteria: Rate limiting fires at configured threshold. Legitimate parallel clients unaffected. Log evidence captured in Micetro.
BGP-10 BGP Authentication & Strict Prefix Filtering — Market Isolation Security

Objective: Verify that BGP session MD5 authentication is enforced and that strict prefix filtering prevents any route leakage between Market tenants or advertisement of non-anycast prefixes.

  • Attempt BGP peering without MD5 password from a test router — confirm session is rejected. Check FRR log: journalctl -u frr | grep -i "auth".
  • Attempt to advertise a non-anycast prefix (e.g., 192.168.16.0/24) via vtysh -c "conf t" -c "router bgp 64512" -c "address-family ipv4 unicast" -c "network 192.168.16.0/24" — confirm Equinix router does NOT accept it (prefix-list ANYCAST-ONLY blocks it). Coordinate with network team to verify on Equinix.
  • Verify Market VRFs cannot receive routes from other Market VRFs via the Equinix route table — network team runs show route vrf MARKET-NA and confirms only CORP prefixes and its own market prefix are present.
  • Success Criteria: MD5 authentication enforced on all BGP sessions. Prefix-list blocks all non-anycast advertisements. Market VRF route tables confirm zero cross-market leakage.
BGP-11 Data Integrity & TSIG Zone Transfer Validation Data Integrity

Objective: Confirm all six Edge Resolvers have received complete, consistent zone data from the MDDS hidden primary via TSIG-secured AXFR/IXFR.

  • Query SOA serial from MDDS: dig @192.168.0.30 SOA corp.pri +short | awk '{print $3}' — note serial number.
  • Query SOA serial from all six Edge Resolvers and confirm they match MDDS serial:
    for h in 192.168.16.20 192.168.16.21 192.168.20.20 192.168.20.21 192.168.30.20 192.168.30.21; do echo -n "$h: "; dig @$h SOA corp.pri +short | awk '{print $3}'; done
  • Attempt AXFR without TSIG key — must be refused: dig @192.168.16.20 AXFR corp.pri should return REFUSED.
  • Increment a test record on MDDS, wait for IXFR propagation, re-query from all Edge Resolvers to confirm update received within zone TTL.
  • In Micetro Central: check zone transfer history for all servers — all should show Success with matching serial.
  • Success Criteria: All Edge Resolvers have identical SOA serial as MDDS. AXFR without TSIG key is refused. Incremental updates propagate within configured refresh interval.
