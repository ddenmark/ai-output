Anycast Architecture Overview
§ 01
The global anycast DNS architecture deployed for this QSR operator is purpose-built around a single foundational principle: every restaurant, in every country, on every cloud, must resolve DNS in under 5 milliseconds with zero dependence on a single point of failure. Anycast achieves this by advertising the same IP address — 10.100.100.100/32 — simultaneously from multiple geographically distributed Edge Resolver nodes across Azure, AWS, and GCP. The Internet's BGP routing protocol automatically steers each DNS client to the topologically nearest healthy node. No client-side configuration, no load balancer, no DNS round-robin hack. Just BGP shortest-path selection, updated within 30 seconds of any failure.

The addition of a Regional ECS VIP (10.100.100.102/32) extends this further by enabling EDNS Client Subnet geo-awareness: content delivery, application routing, and regional failover are all DNS-signaled using the actual client subnet, not the resolver's IP. This unlocks geo-steering for latency-sensitive QSR applications (POS transaction endpoints, kitchen display systems, digital ordering APIs) across global markets without requiring any application-layer changes.

Equinix Fabric serves as the private IP-WAN backbone interconnecting all three cloud providers. This means DNS traffic from POS terminals in Frankfurt, Tokyo, São Paulo, or Chicago never traverses the public Internet — it rides a private 10 Gbps circuit from each CSP directly into the Equinix backbone, then to the nearest Edge Resolver. This architecture is inherently cloud-agnostic: adding a fourth CSP, a new geographic region, or a new market entity is an additive operation — deploy a new Edge Resolver pair, advertise the same VIP, and the global DNS fabric absorbs it automatically.

Why This Architecture Is Designed This Way

Cloud-Agnostic Resilience

No single cloud provider is required for DNS availability. Any CSP region can fail completely and the remaining Edge Resolver nodes absorb all traffic through BGP anycast. The architecture was designed to never have Azure, AWS, or GCP as a single point of DNS failure — a critical requirement given 24×7 restaurant operations.

Private WAN — Zero Internet Exposure

All DNS traffic between POS terminals and Edge Resolvers traverses Equinix Fabric private circuits — never the public Internet. This eliminates DNS-over-Internet latency variance, DDoS exposure from public resolvers, and ISP-level DNS interception. Equinix fabric provides deterministic, SLA-backed sub-10ms cross-cloud latency.

Operational Simplicity at Scale

48,000 restaurants cannot each have individually managed DNS configurations. Anycast collapses all DNS complexity into a single IP address pushed via DHCP Option 6. Adding a new restaurant requires no DNS infrastructure change — the Meraki DHCP relay delivers the anycast VIP automatically at onboarding.

mcd.com — Shared Application Zone (Split-DNS)

mcd.com is the primary consumer-facing and internal application domain. It operates as a split-horizon DNS zone: the external authoritative view is served by public DNS (Akamai Edge DNS / Cloudflare), while the internal view is served exclusively by BlueCat Edge Resolvers. Internal records are never published externally; external records may be replicated inbound via one-way zone transfer for consistency.

One-Way Zone Transfer: External → MDDS

Selected public records from mcd.com are transferred one-way from Akamai Edge DNS to MDDS as a secondary zone. MDDS then serves these records internally alongside internal-only records, ensuring consistency for CORP clients needing to resolve the same FQDN with the internal answer. Outbound zone transfers from MDDS to public DNS are strictly prohibited.

# MDDS — Receive one-way AXFR from Akamai Edge DNS for mcd.com public records
# MDDS is secondary/slave for the external zone only

  type slave;
  masters { 23.211.x.x; 23.211.y.y; }; # Akamai Edge DNS master IPs
  allow-transfer { none; };              # No outbound from MDDS
  # MDDS applies an internal view override on top of this data
  # Internal view ACL overrides specific records for RFC-1918 clients
};

Coexistence Model & DNS Transition States
§ 12a
The existing DNS environment uses Active Directory Domain Controllers as DNS servers, with their IP addresses delivered directly to clients and cloud workloads via DHCP Option 6 and VNet/VPC DNS settings — there is no legacy anycast VIP, and this architecture varies by region. The coexistence model defines four discrete, observable transition states through which every client and cloud workload passes, without any application configuration change. The only levers at each boundary are: DHCP Option 6 (clients), VNet/VPC DNS settings or cloud-native forwarding rules (cloud workloads), and shadow-mode forwarding on BlueCat Edge Resolvers (safety net). Rollback to AD DC DNS is achieved by reverting DHCP scopes and VNet/VPC DNS settings — not via BGP, which is purely an internal BlueCat infrastructure mechanism. During State 3 hypercare, a secondary DNS IP (the nearest AD DC) is retained in DHCP alongside the BlueCat VIP to provide automatic client-side fallback if the anycast VIP becomes unreachable.

Four Transition States

  State 1 — Pre-Cutover

AD Domain Controllers serve as the sole DNS servers for all clients and cloud workloads. DHCP Option 6 delivers two region-specific DC IP addresses per region (unicast — no anycast). VNet and VPC DNS settings point directly to these DC IPs. BlueCat MDDS and Edge Resolvers are deployed in parallel and advertising the anycast VIP in BGP shadow mode (LP 50), but no client has the BlueCat VIP in their DNS configuration. Zone data is being built on MDDS — either imported from AD DNS exports or created fresh. All DDNS updates flow exclusively to AD DCs.

Duration: Jan 6 – Feb 28 (Build Phase). AD DCs remain fully authoritative throughout.
  State 2 — Shadow Parallel Validation

DHCP and VNet/VPC DNS settings remain unchanged — clients and cloud workloads still resolve via AD DC IPs. A comparison engine routes identical test queries to both AD DCs and BlueCat Edge Resolvers (via direct Edge VM IP, not anycast VIP) and validates response parity. Cloud-native forwarding rules and Azure PDNS Resolver rulesets are created in each CSP but are not yet associated to production VNets or VPCs. Shadow-mode forwarding on Edge Resolvers is configured, pointing to AD DC IPs as upstream, and ready to act as a safety net once activated. Minimum 72-hour response parity is required before proceeding to State 3.

Triggered by: completion of Build Phase gate review. Rollback: already on AD DCs — no action needed.
  State 3 — Post-Cutover (Hypercare)

DHCP Option 6 is updated in Micetro to: Primary = 10.100.100.100 (BlueCat anycast VIP), Secondary = nearest AD DC IP for that region. The secondary provides automatic client-side DNS fallback if the anycast VIP is unreachable — without operator intervention. VNet/VPC DNS settings or cloud-native forwarding rules are activated, routing internal zone queries to BlueCat. Shadow-mode forwarding on Edge Resolvers points to AD DC IPs for any records not yet in MDDS — these queries decrease toward zero during the 2-week hypercare window. DHCP lease times are pre-shortened to 2–4 hours before cutover to bound the rollback window. AD DCs remain running and authoritative in AD replication but receive progressively fewer external DNS queries.

Rollback (State 3 → State 1): Revert DHCP Option 6 in Micetro from BlueCat VIP back to DC IPs. Propagates within the pre-shortened lease time (2–4h). VNet/VPC DNS reverted immediately. No BGP change required — AD DCs never stopped running.
  State 4 — Migration Complete

Shadow-mode forwarding to AD DC IPs is disabled on all Edge Resolvers — all records now authoritative in MDDS. DHCP Option 6 is updated to BlueCat VIP only (secondary AD DC IP removed). DDNS flows exclusively to MDDS. AD Domain Controllers continue to run Windows DNS for AD-internal purposes (DC locator, SRV record replication between DCs) but receive no external client DNS queries. The Windows DNS server role on each DC may eventually be disabled as a separate decommission task — AD itself remains fully operational. BGP anycast failover between Edge Resolvers continues as the HA mechanism within the BlueCat tier.

Target: Dec 12, 2027. AD DNS server role decommission: scoped to Q1 2028 post-project (separate work order).

Playbook — playbooks/bluecat-dns-records.yml

This playbook manages the complete DNS record lifecycle via the Micetro Central REST API. It mirrors the Terraform record workflow from §33 — creating TXT, A, PTR, and CNAME records for an Azure App Service provisioning event — but is designed for ad-hoc, pipeline-triggered, or CMDB-driven record changes where Terraform state is not appropriate. All API calls use idempotent GET-then-POST/PUT patterns — running the playbook twice produces no duplicate records. 
# playbooks/bluecat-dns-records.yml
# Usage:
#   ansible-playbook playbooks/bluecat-dns-records.yml \
#     -i inventory/production \
#     -e "app_name=pos-api-na env=prod \
#         app_ip=192.168.16.200 \
#         dns_zone=mcdapps.com \
#         dns_view=CORP \
#         state=present"
#
# state=present  → create records
# state=absent   → remove records
---
- name: BlueCat DNS Record Lifecycle — Micetro REST API
  hosts: localhost
  connection: local
  gather_facts: false
  vars_files:
    - ../vault/secrets.yml

  vars:
    micetro_url:   "https://micetro.infra.mcdapps.com"
    micetro_auth:
      url_username: "{{ vault_micetro_user }}"
      url_password: "{{ vault_micetro_pass }}"
      validate_certs: true
    app_fqdn:      "{{ app_name }}.{{ dns_zone }}"
    verify_fqdn:   "_verify.{{ app_name }}.{{ dns_zone }}"
    cname_fqdn:    "api.{{ dns_zone }}"
    ptr_zone:      "16.168.192.in-addr.arpa"
    ptr_octet:     "{{ app_ip.split('.')[-1] }}"
    ptr_fqdn:      "{{ ptr_octet }}.16.168.192.in-addr.arpa"

  tasks:

    # ── 0. Authenticate — obtain Micetro session token ────
    - name: Authenticate with Micetro Central
      ansible.builtin.uri:
        url: "{{ micetro_url }}/api/v2/auth/login"
        method: POST
        body_format: json
        body:
          username: "{{ vault_micetro_user }}"
          password: "{{ vault_micetro_pass }}"
        validate_certs: true
        status_code: 200
      register: micetro_login
      no_log: true

    - name: Set session token fact

Traffic engineering governs which Edge Resolver VMs receive DNS query traffic across the 18 CSP-region deployment — without changing a single DNS record. All steering is achieved by manipulating the BGP attributes that the Edge Resolver VMs advertise toward Equinix Fabric: Local Preference, AS-Path prepending, MED, and BGP Communities. DNS over HTTPS (DoH) — RFC 8484, Port 443

DoH tunnels DNS queries inside HTTPS on port 443 — indistinguishable from web traffic at the network layer. The client sends an HTTP POST or GET to https://dns.corplab.pri/dns-query with a binary DNS wire-format payload (application/dns-message). This is the preferred protocol for browser-based clients, corporate workstations, and any device traversing untrusted networks, as DoH on port 443 passes through virtually every enterprise firewall without special rules.
