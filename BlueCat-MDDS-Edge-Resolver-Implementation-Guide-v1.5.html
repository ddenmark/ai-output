Implementation Steps

SECTION DETAILED STEPS
1. Prerequisites (Common)
  1. 1Obtain BlueCat licenses (MDDS 9.x + Edge Service Point v4) and Micetro Central installer.
  2. 2Prepare SSH key pair bluecat-key and admin user bluecat.
  3. 3Ensure Equinix Fabric Cloud Router BGP peering is pre-staged (ASN 64512, VIP 10.100.100.100/32).
  4. 4Install Terraform 1.5+ locally (or use manual Marketplace deployment).
  5. 5Prepare Windows Server 2022/2025 VM in Azure East US 2 for Micetro Central.
  6. 6Open required ports: UDP/TCP 53 (DNS), TCP 179 (BGP), TCP 443 (Micetro/BlueCat consoles).
2. Deploy Micetro Central on Windows
  • Deploy a dedicated Windows Server VM in the corporate hub VNET (Azure East US 2 recommended).
  • Download latest Micetro Central installer from BlueCat customer portal.
  • Run installer → select Central role → join to AD domain corp.root.
  • After installation, access console at https://micetro-central.corp.example.com.
  • Add all future BlueCat appliances (MDDS + Edge) by IP address and approve.
  • Configure Micetro for zone management (prepare for NA AD zone import per workshop session 1.3A).
3. Micetro RBAC – LDAP Groups & Role-Based Access

Prerequisites: Micetro Central is domain-joined to corp.root and LDAP authentication is enabled.

  1. In Active Directory (corp.root), create the following security groups:
    DDI-Admins, DDI-Engineers, DDI-Developers, DDI-ReadOnly
  2. In Micetro Central console → Administration → Users & Groups → Import from LDAP.
  3. Search and import the four DDI groups.
  4. Assign roles:
    • DDI-Admins → Full Administrator role
    • DDI-Engineers → Engineer role (full configuration rights)
    • DDI-Developers → Developer role (zone & record management)
    • DDI-ReadOnly → Read-Only role (view-only access)
  5. Apply any custom restrictions (e.g., limit DDI-Developers to specific zones or clouds).
  6. Test login with a member of each group to confirm appropriate permissions.
4. Configure TLS Certificates (with SAN Support)
  1. Request certificates from the corporate PKI (or Let’s Encrypt / internal CA) for each BlueCat appliance and Micetro Central.
  2. In the certificate request, include the following Subject Alternative Names (SANs):
    • Primary FQDN (e.g., mdds-az-01.dns.corp.example.com)
    • Shortname alias (mdds-az-01)
    • Anycast VIP hostname (dns.corp.example.com)
    • IP address of the anycast VIP (10.100.100.100)
  3. Upload the signed certificate + private key via the BlueCat appliance web UI (System → TLS Certificate).
  4. For Micetro Central: In Micetro console → Administration → Server Settings → HTTPS → upload the certificate bundle.
  5. Restart services and verify HTTPS access on port 443 with no certificate warnings.
  6. Confirm shortname alias resolution works (e.g., https://mdds-az-01 loads correctly).

6. Azure East US 2 Deployment (HA Pair)

DNS Subnet: 192.168.16.0/24 • Use Terraform from architecture report (provider.tf + variables.tf + main.tf).

  1. Create resource group rg-bluecat-dns-prod-eastus2.
  2. Deploy 2× MDDS VMs (192.168.16.10 / .11) using Azure Marketplace image BlueCat MDDS 9.x.
  3. Deploy 2× Edge Resolver VMs (192.168.16.20 / .21) using BlueCat Edge Service Point v4.
  4. Add secondary private IP 10.100.100.100/32 to each VM NIC (anycast VIP).
  5. Configure NSG: Allow UDP/TCP 53, TCP 179 (BGP), SSH 22.
  6. SSH to each VM as bluecat and run FRR/BGP config:
    sudo apt update && sudo apt install frr -y
sudo vtysh -c "configure terminal" -c "router bgp 64512" -c "bgp router-id <VM-PRIMARY-IP>" -c "neighbor <EQUINIX-ROUTER-IP> remote-as 65515" -c "address-family ipv4 unicast" -c "network 10.100.100.100/32" -c "exit-address-family" -c "end" -c "write"
sudo systemctl restart frr
  7. In Micetro Central: Add servers → configure MDDS as Authoritative, Edge as Recursive with shadow-mode forwarding to legacy AD DCs.
Health Checks (Azure):
• dig @192.168.16.20 www.example.com
• vtysh -c "show ip bgp summary" (peers Established)
• Micetro Servers dashboard (green sync status)
• curl -I http://localhost:8080 (Edge health)
7. AWS us-east-2 Deployment (HA Pair)

DNS Subnet: 192.168.20.0/24 (multi-AZ) • Use Terraform from architecture report.

  1. Deploy 2× MDDS VMs (192.168.20.10 / .11) using AWS Marketplace AMI BlueCat MDDS 9.x.
  2. Deploy 2× Edge Resolver VMs (192.168.20.20 / .21) using BlueCat Edge Service Point v4.
  3. Assign secondary private IP 10.100.100.100 on each ENI.
  4. Attach to TGW (ASN 64512) and configure Security Group (UDP/TCP 53 + BGP 179).
  5. SSH to each VM and apply identical FRR/BGP config (neighbor uses TGW ASN 64512).
  6. Add servers to Micetro Central.
Health Checks (AWS):
• Same DNS + BGP checks as Azure
• aws ec2 describe-network-interfaces --network-interface-ids <ENI> (confirm secondary IP)
• nslookup www.example.com 10.100.100.100 (local test)
8. GCP us-east4 Deployment (HA Pair)

DNS Subnet: 192.168.30.0/24 • Use Terraform from architecture report.

  1. Deploy 2× MDDS VMs (192.168.30.10 / .11) using image projects/bluecat-public/global/images/bluecat-dns-for-gcp.
  2. Deploy 2× Edge Resolver VMs (192.168.30.20 / .21) using bluecat-edge-service-point-v4-for-gcp.
  3. Configure alias IP range 10.100.100.100/32 on each network interface.
  4. Create Cloud Router (ASN 16550) and firewall rules for DNS + BGP.
  5. SSH to each VM and apply FRR/BGP config (neighbor = Cloud Router IP).
  6. Add to Micetro Central.
Health Checks (GCP):
• gcloud compute instances describe <VM> --show-metadata (verify alias IP)
• Same DNS/BGP/Micetro checks

10. BGP Testing Scenarios (After Network Advertisement)
  1. Scenario 1 – Basic Failover
    Run continuous nslookup www.example.com 10.100.100.100 (from a test client). SSH to one Edge VM and run sudo systemctl stop frr → confirm <5s convergence to remaining nodes (workshop 1.2).
  2. Scenario 2 – AS-Path Prepending
    On one VM run:
    vtysh -c "configure terminal" -c "neighbor <peer> route-map PREPEND out"
    Monitor route preference shift in vtysh -c "show ip bgp 10.100.100.100".
  3. Scenario 3 – Full Cloud Withdrawal
    Stop FRR on both Azure nodes → verify traffic instantly shifts to AWS/GCP nodes → re-enable and confirm return.
  4. Scenario 4 – Health-Based Withdrawal
    Simulate high CPU on one Edge Resolver (or implement BlueCat health probe) → confirm automatic BGP withdrawal and traffic failover.
11. Azure DHCP Options & Client VNet Configuration

Azure fully manages DHCP for all VMs in a Virtual Network. Only Option 6 (DNS Servers) is controllable at VNet level.

DHCP OptionAzure Configuration MethodValue in POCEffect
Option 6 (DNS Servers)dns_servers in azurerm_virtual_network["10.100.100.100"]Windows 11 workstations receive BlueCat anycast VIP after lease renewal
 
resource "azurerm_virtual_network" "client_vnet" {
  name                = "vnet-client-eastus"
  location            = "eastus"
  resource_group_name = "rg-qsr-test-workstations"
  address_space       = ["10.20.0.0/16"]
  dns_servers         = ["10.100.100.100"]
}

Existing VMs: ipconfig /release && ipconfig /renew or reboot. New VMs receive immediately.
12. Testing BlueCat DHCP Functionality in Cloud-Hosted Workloads

Azure Limitation: Azure hypervisor DHCP is mandatory. BlueCat DHCP serves via unicast / relay only.

  1. Configure DHCP scopes in Micetro Central on Edge/MDDS appliances (DNS option = 10.100.100.100).
  2. Deploy small Linux relay VM in client VNet or use dhtest simulator on existing Windows 11 VMs.
  3. Relay example (isc-dhcp-relay):
    sudo apt install isc-dhcp-relay
    Edit /etc/default/isc-dhcp-relay → SERVERS="<BLUECAT-DHCP-IP>"
  4. Simulator test:
    sudo dhtest -i eth0 -r <BLUECAT-DHCP-IP> -m 00:11:22:33:44:55 -c 5
  5. Verify leases in Micetro → DHCP → Leases and confirm DNS option on clients.
13. TSIG Verification Steps (DDNS Security)
  1. In Micetro Central → Administration → TSIG Keys → Generate key (name: qsr-ddns-tsig, HMAC-SHA256).
  2. Assign key to zone(s) → Properties → TSIG Key for Dynamic Updates.
  3. On Windows 11 test VM: ipconfig /release && ipconfig /renew && ipconfig /registerdns
  4. Verify in Micetro: DNS → Zone → Records (look for “Signed” or audit log entry).
  5. Test failure: Remove key temporarily → confirm rejection in logs.
14. Conditional DNS Servers via DHCP (Global Anycast vs ECS/Regional)

Global Anycast path (default): Scope → IPv4 Options → Option 6: 10.100.100.100

ECS-aware / Regional path:

  1. Create Client Class in Micetro (based on Option 82, MAC, subnet, or Vendor Class).
  2. Assign class → Option 6: specific regional Edge Resolver IP (e.g., Azure East US 2 Edge 192.168.16.20).
  3. Enable ECS on target Edge Resolver → DNS → Resolver → Advanced → Client Subnet Support.
  4. Windows 11 VMs (via relay) will receive the appropriate DNS server based on class.
  5. Verify: ipconfig /all | findstr "DNS Servers"
15. Packet Capture & Traffic Analysis (Wireshark + netsh ETW + ETL to PCAP)

Purpose: Capture and analyze DHCP requests, DNS queries to the anycast VIP, TSIG-signed DDNS updates, and BGP traffic on Windows 11 test workstations.

  1. Install Wireshark on each Windows 11 VM:
    Download latest installer from https://www.wireshark.org/download.html → Run as Administrator → Complete installation (include Npcap).
  2. Start Windows Event Tracing (netsh) capture (elevated Command Prompt):
    netsh trace start capture=yes tracefile=C:\DNS-DHCP-Capture.etl maxSize=512 report=disabled
  3. Reproduce traffic: Run ipconfig /release, ipconfig /renew, ipconfig /registerdns, and DNS queries against 10.100.100.100.
  4. Stop the trace:
    netsh trace stop
  5. Download etl2pcapng (latest release from GitHub: https://github.com/microsoft/etl2pcapng/releases).
    Place etl2pcapng.exe in C:\Tools and run:
    C:\Tools\etl2pcapng.exe C:\DNS-DHCP-Capture.etl C:\DNS-DHCP-Capture.pcapng
  6. Open the PCAP in Wireshark:
    File → Open → C:\DNS-DHCP-Capture.pcapng
    Apply display filters:
    • dhcp (DHCP offers/acks)
    • dns (queries to 10.100.100.100)
    • dns.tsig (TSIG-signed updates)
    • bgp (if capturing from appliances)
  7. Save the .pcapng for workshop documentation or troubleshooting.
Tip: Run the netsh trace on multiple Windows 11 VMs simultaneously for parallel client-side validation of DHCP option propagation and anycast resolution.
